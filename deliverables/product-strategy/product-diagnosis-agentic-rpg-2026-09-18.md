## 📌 TL;DR（执行摘要）

- **核心目标**：回答一个问题——**"我加了很多功能、工具，但效果不好、越来越复杂，而且下班后没动力玩"到底病在哪。**
- **关键决策**：**病因不是"功能太多"，而是"形态错配"（分两层）+ "反馈回路缺失"。** 功能过剩只是症状。
- **最强证据（来自产品自己的分析）**：产品投入最大工具面（约 26 个玩法机制工具：检定/战斗/委托/升级/光锥/技能/营地）服务"战斗·冲突·成长"；而**产品自己生成的 11 份实质玩家画像里，9 份明确写着"回避战斗、冲突或严肃剧情"（90%）**。
- **反直觉发现**：**"留不住人"不成立**。本地快照下可证实的累计回合 **≥3931**，单档最高 **1062**、次高 **512**。真正的问题是 **"玩得长 ≠ 玩得爽"**——玩家每回合要产出指令 + 承受 800~1160 字阅读 + 维持叙事连贯，**三项都是认知成本，且零即时反馈**。
- **形态错配的两层（关键区分）**：
  - **方向错配（工程层）**：26 个机制工具服务的方向，与 90% 玩家的偏好**相反** → **被浪费的工程投入**。
  - **形态错配（体验层）**：玩家要"被叙事舒服地包住"，产品却要求"高产出 + 高阅读 + 零反馈"的**主导式劳动** → **需求方向对了，交付形态错了**。
- **最可执行的抓手**：玩家要的是「**掌控感 without 认知劳动**」——而产品里恰好有这个机制（`publish_reward_choices` 给选项让玩家选），**却只被调用过 1 次**。改造方向 = **AI 提议 2–3 个走向，玩家点头/微调/否决**，而不是"玩家自己写下一幕"。
- **下一步**：① 先做 1 天的**形态裁决**（最高 RICE）；② 修复 3 个 P0 体验缺陷；③ 把 65.3% 的隐形记账"真正隐形"并做可见化改造；④ 个人侧执行"开发/游玩物理分离"。

## 2.2 复杂度债务量化

### 三大债务源

**① NPC 记账占比 65.3%** —— 引擎被记账淹没。LLM 每回合把大量预算花在"维护状态机内部一致性"上，而非讲故事。

**② 配置项注册缺口** —— 94 个配置项，只有 **30 个**进入统一注册表，**未注册率 68.1%**。新功能加配置时没有强制登记入口，复杂度无法收口。

**③ 工具-技能映射断裂** —— `TOOL_SKILL_MAP` 50 条中 **6 条指向不存在的技能目录**（牵连 **14 个工具**）：
- `rpg-mirror-mechanics` → 7 个工具（**镜像系统整条断链**）
- `rpg-area-story` → 3 个工具
- `memory` / `rpg-story-hook` / `scene-mgmt` / `style` → 各 1 个

另有 **2 个无主技能**：`rpg-festival`、`rpg-weather`（有目录、无任何工具映射）。

### 复杂度负债指数（CDI）

> **CDI = 100 × [ 0.35·(玩家不可见调用占比) + 0.25·(配置未注册率) + 0.20·(映射断裂率) + 0.20·(僵尸∪遗留工具率) ]**

| 因子 | 权重 | 实测值 | 贡献 |
|---|---:|---:|---:|
| 玩家不可见调用占比 | 0.35 | 65.3% | 22.9 |
| 配置未注册率 | 0.25 | 68.1% | 17.0 |
| 映射断裂率 | 0.20 | 28.6% | 5.7 |
| 僵尸 ∪ 遗留工具率 | 0.20 | 35.6% | 7.1 |
| **CDI** | — | — | **≈ 53 / 100** |

**读数：中度偏高复杂度负债。** 主要债务来自"玩家看不见的记账逻辑"和"2/3 配置项失管"。

# 第三部分 · 用户与动机诊断（为什么不愿意玩）

## 3.1 双重身份的绞杀（解释开发者本人）

产品里有两种奖励在争夺同一个大脑：
- **改代码的奖励**：即时、确定、完全可控 —— 每一次改动都"成功了"。
- **玩游戏的奖励**：延迟、随机、不可控 —— 每一次游玩都可能"出戏了"。

只要游玩出现任何摩擦，他就有能力立刻切回"改代码"去获得确定性快感。**产品越强，越玩不下去——因为可改的东西越多，逃避的出口就越多。**

**`set_narrative_style` 被调用 372 次**（全系统第 2），不是游玩数据，而是**"我以为我在玩，其实我在调"**的自白。

## 3.2 核心悖论：玩得长 ≠ 玩得爽

> 这是本案最反直觉的地方：**玩家能玩 1000 回合，却"下班没动力开"。**

| 认知成本项 | 实测 |
|---|---|
| 产出成本 | 每回合要构思并写下"下一幕该演什么"（平均 64 字舞台指令） |
| 阅读成本 | 承受 800~1160 字（最长 2231 字）的密集散文 |
| 连贯成本 | 还要维持跨回合的叙事一致性 |
| **即时反馈** | **≈ 0**（掷骰/委托/升级都实现了，但玩家感知不到） |

**三种主流娱乐的对比**：
- 看剧 = 纯消费，零产出
- 打游戏 = 纯操作，即时反馈
- **本产品 = 高产出 + 高阅读 + 零即时反馈 → 三者中最累的组合**

**所以"下班后没动力玩"的答案不是"逃避焦虑"，而是"认知负荷与娱乐形态的错配"。** 这个解释同时适用于那位非开发者——他也能玩 512 回合，但产品自己的画像说，他想要的只是"轻松、亲密、日常、被宠爱"。

## 3.3 SDT（自我决定论）逐项诊断

| 维度 | 诊断 | 判定 |
|---|---|---|
| **自主 Autonomy** | 表层极高（能改一切），深层极低（世界不会因他而真正变化）。有**元层自主**（改产品），缺**世界层自主**（在故事里做有后果的选择） | ⚠️ 错位 |
| **胜任 Competence** | **崩得最彻底且最可推广**——65.3% 的努力不可见，玩家没有进度条、没有反馈、没有"我做到了" | ❌ 崩溃 |
| **关联 Relatedness** | **导演姿态本身反关联**：你无法与一个被你指挥的木偶建立关系 | ❌ 死亡 |

## 3.4 最锋利的一句洞察

> **导演姿态本身反关联：你无法与一个被你指挥的木偶建立关系。**
>
> 这一条现在有**对照组背书**：两个不同的人，用同一种导演姿态，得到了同一种"读得多、动得少"的体验。它比"开发者心理问题"更普遍、也更可修。

**但必须诚实**：其中「关联感结构性死亡」在开发者身上成立（NPC 是他自己写的），**在非开发者身上不成立**（他面对的是别人写好的世界）。所以**真正杀死关联感的，是"导演姿态"，不是"作者身份"。**

## 3.5 一个必须澄清的数据边界

> ⚠️ 项目**已迁移到服务器**，本地 `data/plugin_data/...` 只是**历史快照**，可观测窗口 **2026-05 ~ 2026-07-04**。
> **不得**据此得出"用户已停止游玩 / 停摆 N 天"的结论。所有月度数字都是**下限**。

## 3.6 形态错配的两层拆解（关键区分）

"形态错配"这个词需要拆成两层，因为**它们的解法完全不同**：

| 层次 | 内容 | 证据 | 解法 |
|---|---|---|---|
| **方向错配（工程层）** | 26 个机制工具服务"战斗/冲突/成长/风险"，与 90% 玩家的偏好**相反** | 产品自证画像 9/11 回避战斗侧；唯一想要探险的玩家只玩 14 回合 | **减法**：隐藏/自动化这些工具，把工程投入转向可见反馈 |
| **形态错配（体验层）** | 玩家要的是"**被叙事舒服地包住**"，产品却要求"**高产出 + 高阅读 + 零反馈**"的主导式劳动 | 输入输出比 1:14；输出中位 754 字；玩家输入 64 字舞台指令 | **改造交付形态**：把"你来写下一幕"改成"你来选下一步" |

> **方向错配是"投错了地方"，形态错配是"交付错了形式"。前者靠减法，后者靠重新设计交互。**
> **注意**：形态错配这层意味着——**即使把 26 个机制工具全删掉，问题也只解决了一半。**

## 3.7 最可执行的抓手：玩家要的是「掌控感 without 认知劳动」

把两条证据放在一起看，会浮出一个非常具体的改造方向：

- 玩家画像反复出现"**掌控感**"：如 877459692「乐于在安全轻松的环境中主动调戏并获得正向反馈」、2438094710「支配与服从剧情」、218606013「享受…掌控感」。
- 但玩家**不愿意为掌控感付出认知劳动**：平均只写 64 字，且是"我让X做Y"的**指令式**而非"我该做什么"的**决策式**。

**→ 结论：他们要的是"我能决定走向"的感觉，而不是"我要构思走向"的负担。**

**而产品里恰好有这个机制，却几乎没被用过：**

| 机制 | 设计意图 | 实际调用 |
|---|---|---|
| `publish_reward_choices` | 系统给出选项，玩家**选** | **1 次** |
| `choose_reward` | 玩家做出选择 | **0 次** |
| 契约要求"末尾追加 3-4 个编号选项" | 每回合给玩家**低成本的控制点** | 合规率仅 **44.9%** |

> ### 🎯 这可能是全案性价比最高的一处改造
> **把"编号选项"从"格式要求"升级为"核心交互范式"**：
> - **现在**：AI 写 800 字散文 → 玩家自己想下一幕 → 写 64 字指令（高认知劳动）
> - **改成**：AI 写 800 字散文 + **提议 2-3 个具体走向** → 玩家**点头 / 微调 / 否决**（低认知劳动，保留掌控感）
>
> 这不需要新增任何工具、不违反任何 Non-goal，**只需把已经存在但合规率仅 44.9% 的选项机制做扎实**（对应 P0-2 与 P1-2）。它同时命中：**降低认知负荷 + 提供即时反馈 + 保留掌控感 + 不需要新功能**。

| **Character.AI** | 托管平台，海量 UGC | ★ 极低 | 每日任务 + Charms 经济 | ❌ |
| **AI Dungeon** | 开放文本冒险 | ★★ 低 | 剧情连续性 | ❌ **官方明确"无 game state、无工具调用"** |
| **Talkie / 星野** | 移动端陪伴 + 角色扮演 | ★ 极低 | 好感度 + 抽卡收藏 + TTS + "几天不登录角色会抱怨" | ❌ |
| **猫箱** | 移动端 AI 角色互动 | ★ 极低（"3 分钟熟悉全部操作"） | 签到 + 投稿奖励 + 节日限定 | ❌ |
| **NovelAI** | 叙事质量导向写作环境 | ★★★ 中 | 无 | ❌ |
| **我方** | 本地部署 Agent 化 RPG | ★★★★★★ 极高 | **无** | ✅✅ 重（双流水线） |

> **判断**：整个赛道呈"哑铃形"——一端极简大众产品，一端极客自托管栈。**"有一定深度但开箱可用"的中档目前是空的**——这既是最大机会，也是我方最危险的位置：**我方落在极客端，却没有极客端最重要的两样东西——生态（卡/预设市场）和上手路径。**

## 4.2 三条最重要的竞品结论

1. **"状态机"不是留存的答案，而是留存的成本。** 头部产品几乎都不做传统状态机；AI Dungeon 官方明确无 game state。**Agent 化是差异化机会，但必须服务于可见体验，否则就是自嗨。**
2. **复杂度不是原罪，"复杂度裸露"才是。** SillyTavern 参数比我方只多不少，但它把复杂度**外置**（6 个可插拔组件 + 社区卡库），本体保持薄；我方把它**内置**进 94 个开关。
3. **记忆/一致性是全行业未解痛点**——星野用户 63.8% 抱怨记忆差、65.7% 抱怨剧情连贯性差。**这正是我方状态机架构的价值所在，但必须先被玩家感知。**

> **一条有力背书**：**星野自家的用户研究**（105 份问卷，SUS 67.8 分低于行业平均）结论就是——**"删除或隐藏非必要功能，提供『功能自定义』开关"**。这把我方"隐藏 94 个开关、做一键开局"的定性从"创新"降级为"补课"。

## 4.3 可偷师的三个设计

### 设计一：把 94 个开关变成 1 次"选剧本"——**开局预设包 StarterKit**
- **竞品依据**：SillyTavern 的"预设"是一整套参数打包、可导入导出；猫箱提供 300+ 模板 + 问答式引导，"3 分钟熟悉全部操作"。
- **怎么做**：定义 `StarterKit = 世界观 preset + 起始角色卡 + 风格 skill 组合 + 94 个配置的推荐值`，打包成一个 JSON。首次启动只问 1 题，其余全部走默认。**默认值必须能玩——这是当前最大缺失。**

### 设计二：给"看不见的状态"做一个玩家能看见的面板——**可见状态层**
- **竞品依据**：AI Dungeon 有 Context Viewer；Talkie 把好感度"可视化、进度化"作为核心留存设计；Character.AI 用户第一诉求（46%）就是"可见 + 可编辑"。
- **怎么做**：每回合在正文后附**极简状态条**（地点/时间/关系/当前委托/已埋线索数）；把 65% 的后台记账**抽样外显 1-2 条**（如"XX 对你的好感 +1，因为他记得你上次的帮忙"）；把"伏笔"变成玩家可见的**悬念卡**。

### 设计三：给单机产品装一个"明天回来"的理由——**节奏机制**
- **竞品依据**：Character.AI 靠每日任务 + Charms 经济；猫箱靠签到 + 节日限定。
- **怎么做**（自托管无服务器，用"叙事化"替代"运营化"）：每天首次登录时世界推进一小段（NPC 有昨夜发生的事、季节变化）；每 N 回合留明确悬念 + "下次继续"；把已解锁角色卡/已完成委托做成"图鉴"。

> **Talkie/星野的可视化范式（补充深挖）**：不是一根好感度进度条，而是 **"收藏图鉴 + 阶段解锁 + 徽章"** 三件套。**我方的 28 张 canonical 卡 + 委托 + 伏笔天然就是图鉴与解锁门的内容源——把它们从"内部状态"改为"玩家收藏面板"，是零新增内容、纯暴露层的改造。**

## 4.4 反向洞察：功能深是不是差异化？

**判断：权重是"暴露 70% / 过剩 30%"。**

**支持"功能深是差异化"的证据**：头部都不做状态机，而用户对头部的抱怨高度集中在状态/记忆/一致性/可控性——**这恰好是我方架构的长板**。第二位非开发者用户玩到 512 回合，也说明**深度状态机 + 开箱可用的形态本身是有人需要的**。

**支持"功能过剩"的证据**：65.3% 调用不可见；双流水线并存；94 配置 / 24 skills；调用≈0 的内容型功能——典型的"为架构而架构"。

**结论**：**不要砍功能，要砍"功能的暴露方式"。** 唯一真正的"过剩"是**没有玩家可见反馈的后台记账**。

# 第五部分 · 破局路线图

## 5.1 破什么局：三个候选病因的裁决

| 候选病因 | 证据强度 | 判定 |
|---|---|---|
| **A. 功能太多（表面积过剩）** | 强（实测） | **症状，不是病因**——多不是原罪，裸露才是 |
| **B. 形态错配（产品形态 vs 真实用法）** | **最强**（产品自证 + 双用户交叉） | **第一病因** |
| **C. 没有反馈回路（不可见 + 零即时反馈）** | 强（实测） | **第二病因（与 B 同源，可并行修）** |

> **破局 = 先解决 B（形态错配），同步解决 C（反馈回路），最后用减法收拾 A（表面积）。**
> 三者有**严格的先后依赖**：形态不定 → 反馈回路不知道该为谁建 → 减法不知道该砍谁。

## 5.2 产品定位的一句话收敛

> ### 「一个开箱即玩的中文单人跑团——深度世界状态藏在引擎里，玩家第一分钟就看得见它。」
>
> 三个必须同时成立的定语：
> 1. **开箱即玩**（StarterKit，94 配置 → 1 次选择）→ 解决上手成本
> 2. **单人跑团**（有规则、有后果、玩家会介入机制的中间态）→ 解决形态错配
> 3. **深度可见**（关系图鉴 / 悬念卡 / 状态条）→ 解决 65.3% 不可见

**对竞品方向的评估**：认同"中文硬核 RP + 自托管"70%；但**不要学 SillyTavern 的"前端容器"定位**（那是创作者工具，不是游戏），且**状态机必须服务"可见反馈"，而不是服务"内部记账"**。

| **Step 4 · 隐藏** | 双流水线一条、24 skill、记账工具、镜像/光锥移出默认路径 | 数据表保留，仅停止暴露 |
| **Step 5 · 删除** | 1 版本后：删别名、删孤儿工具、删废弃配置、归档 reviewer | 删除前**打 git tag**；数据表迁移到 `archive/` 而非 `DROP` |
| **Step 6 · 验证** | 用 CDI + 合规率 + 失败率 + 可见调用占比验收 | 旧存档可正常读取 = 迁移成功 |

# 第六部分 · 人如何改变（个人行为方案）

## 6.1 用福格模型 B=MAP 拆解："下班后打开它"为什么没发生？

| 要素 | 现状 | 处方 |
|---|---|---|
| **动机 M** | 外在动机（造东西）**极强**；内在动机（玩）**弱且被吞噬** | **不救动机**（救不动）。用结构兜底 |
| **能力 A** | **极低**——启动要选卡、要等首字、要读 800~1160 字、要想"我接下来该说什么"、要忍受后台噪音 | **主战场。** 把"玩一次"的启动成本降到接近零 |
| **提示 P** | **缺失**——没有"该玩了"的触发；但"改代码"的触发**无处不在**（bug、灵感、IDE） | **植入游玩提示**，并**物理隔离开发提示** |

> **关键洞察**：**"继续玩"和"开始玩"是两种完全不同的成本。**
> - 冷启动成本（高）= 重建上下文 + 选世界观 + 定前提 + 入戏 → **这是决策点**
> - 持续成本（低）= 追加一句反应即可续命 → 所以档能长到 512/1062 回合
> - → **"档很长"衡量的是耐力与沉没投入，不是愉悦。破局要打的是冷启动成本。**

## 6.2 双边责任表

| 产品要改（工程侧） | 他自己要改（行为侧） |
|---|---|
| 后台记账静默化，49 工具 → ~10 个可见 | **接受更少的控制权**，把旋钮交出去 |
| 伏笔/记忆/奖励自动化 | **停止在游玩中调参**（`set_narrative_style` 372 次需冷处理） |
| 可见后果叙事化（好感度"演出来"） | **建立"先玩后改"的规则**并执行 |
| 一键继续 + 自动"上回说到"开场 | **分离开发/游玩的时间、设备、账号** |
| 手动风格切换改为自动/隐藏 | **给游玩设结束仪式，允许自己"玩完"** |
| 长档支持 | **忍受不完美**，不因一点小瑕疵就重开 |
| StarterKit（94 配置 → 1 次选择） | **做出 M3 的选择**：承认自己更想守护的是"玩"还是"造" |

> **核心判断**：产品侧的问题（不可见、手动、高摩擦）是**可以工程解决的**；他自身的问题（逃避、控制欲、身份混淆）**只能靠规则和环境设计来对冲，靠意志力没用**。

## 6.3 三个最关键的行为改变动作 ★

### ★ 动作 1：把"开发模式"与"游玩模式"在物理上分离（账号 / 设备 / 时间三分离）

| 分离维度 | 具体做法 | 解决什么 |
|---|---|---|
| **不同账号** | 建一个**"玩家账号"**：无权访问管理台/配置/调试工具，看不到 49 工具调用，只能看到叙事输出。**把旋钮从他手里拿走** | 控制权冲突 |
| **不同设备/入口** | **游玩用手机/网页端**（低摩擦、纯消费）；**开发用 PC 终端** | 注意力冲突 |
| **不同时间块** | 设"开发时段"与"游玩时段"，互不重叠 | 时间冲突 |

> 这是**唯一一条能同时解决"控制权冲突、注意力冲突、时间冲突、奖励冲突"的措施**。

### ★ 动作 2：降低启动摩擦到接近零（一键继续 + 自动"上回说到"）

- 一键启动 → 自动载入最近存档 → 直接给一段开场钩子。
- **把"从零进入"变成"被世界拉进去"**：从"我要不要开始"变成"我已经在里面了"。
- 产品侧交付 = StarterKit + 自动开场；行为侧交付 = 一条规则：**"打开产品 = 直接继续，不先看代码"**。

### ★ 动作 3："先玩 20 分钟再改代码" + "待改清单"延迟机制 + 结束仪式

| 子动作 | 具体规则 | 解决什么 |
|---|---|---|
| **先玩后改** | 每次打开产品，**强制先玩满 20 分钟**，期间禁止进入开发环境 | 把"改代码的即时奖励"往后推，给"游玩的延迟奖励"腾出生长空间 |
| **待改清单** | 想到的改进**写进"待改清单"**，不立即执行 | 打断"想到改进 → 立刻切走"的身份切换 |
| **结束仪式** | 每次结束前**主动写一句"本回结束 + 一句话小结"** | 让 session **有意识地结束**，而不是"腻到关掉" |

## 6.4 成功标准的重构

| 旧 KPI（"造"） | 新 KPI（"玩"） |
|---|---|
| 发了多少功能 / 多少 commit | **不重开的最长回合数** |
| 工具数量 / 配置项数量 | **完整玩完的 session 数** |
| CDI 上升 | **CDI 不上升**（护栏指标） |
| 新系统上线 | **玩家可见调用占比 ≥ 1.5/回合** |

## 6.5 分叉：如果他的真实动机是"造"而不是"玩"

**必须诚实面对这个可能。** 如果是这样，两条路线完全不同：

| 路线 A · 想玩 | 路线 B · 想造 |
|---|---|
| 目标：**自己成为这个世界的玩家** | 目标：**把它做成别人愿意玩的作品** |
| 核心动作：减法 + 可见化 + 物理分离开发/游玩 | 核心动作：**StarterKit + 文档 + 内容包 + 让第二用户（942361330）成为真实测试者** |
| 北极星：不重开的最长回合数 | 北极星：**第二个用户的留存与主动反馈** |
| 不需要：社区化、市场、UGC | 需要：上手路径、内容供给、可分享预设包 |
| 风险：产品成为私人玩具 | 风险：**单机自研永远缺"内容飞轮"和"运营者"** |

> **注意**：**第二位非开发者用户已经玩了 512 回合**——路线 B 并非从零开始，它已经有第一个真实用户了。这是这个产品最被低估的资产。
