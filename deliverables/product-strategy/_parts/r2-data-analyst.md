## 4. ④ 权威总量与"3931 是下限"

### 4.1 权威回合总数
**3931**（18 个 ic>0 会话的 `game_sessions.interaction_count` 之和，无截断）。**与简报一致。** 该值**不含** reset 前的回合。

### 4.2 ★ reset 的痕迹：**找到了直接指纹**

代码事实：
- `/rpg reset` → `db.wipe_session()`：**`DELETE FROM` 所有表 + VACUUM**（`database.py:1169-1189`）→ **清空但保留 AUTOINCREMENT 水位**。
- `/rpg memory clear` → 删 `episode_memories`+`semantic_chronicles`，并 **`UPDATE game_sessions SET interaction_count = 0`**（`commands.py:1387-1408`）→ **回合计数归零**。
- `npc_events` 被**主动裁剪**（每 NPC 保留最近 10 条 encounter，`state_machine.py:603-613`）→ **不能**用 npc_events 作 reset 指纹。
- **`visible_events` 在代码中只增不删**（全库仅 `INSERT`/`UPDATE`，唯一删除路径是 `wipe_session`）→ **`visible_events` 的 AUTOINCREMENT 水位 > 现存行数 = 发生过 `/rpg reset` 的干净指纹**。

**扫描结果（`task4b_reset.py`）——5 个会话命中指纹：**

| session_id | ic | visible_events 曾插入 | 现存 | **被抹除** |
|---|---:|---:|---:|---:|
| **default:FriendMessage:245432630** | **12** | **233** | **6** | **227** |
| default:GroupMessage:909871205 | 53 | 116 | 38 | 78 |
| default:GroupMessage:1098307480 | 47 | 41 | 11 | 30 |
| default:GroupMessage:289584858 | 291 | 121 | 100 | 21 |
| default:GroupMessage:529384034 | 134 | 22 | 11 | 11 |
| **合计** | | | | **367** |

- 最触目：**负责人好友档 `FriendMessage:245432630`，ic 仅 12，却曾插入 233 条 visible_events / 504 条 npc_events**（现仅存 6 / 5）→ 该档在 reset 前**有数百回合的历史**，被抹除后计数只剩 12。**这单独证明了 `interaction_count` 会严重低估。**
- **"同一 session 多个世界库"**：命中 2 处 —— `FriendMessage:245432630`（`world_default_*` + `world_狼人杀_*`）、`GroupMessage:1027533701`（`world_default_*` + `world_狼人杀_*`）。两处狼人杀库**均为 0 行**（建了世界未玩）→ 与"开新世界/新 preset"一致。
- `updated_at < created_at` 异常：**0 处**（该线索无产出）。

### 4.3 3931 作为下限的估计区间

- 被抹除 visible_events = **367**。
- 无 reset 会话的基线密度 = **0.199 visible_events/回合**（pooled，11 个干净会话、3234 回合；单会话区间 0.078–0.528）。
- → 被抹除回合 ≈ `367 / 0.199 ≈ **1844**`（密度敏感：0.528→695；0.078→4705）。

> **结论**：
> - **严格下限：3931**（已被 reset 机制 + 指纹证据共同证明为下限）。
> - **真实累计回合合理区间：约 4,800 – 5,800**（中心估计），**保守上界 ~8,600**。
> - **置信度：下限=高；区间=低**（密度假设噪声大，且 `memory clear` 与 reset 的先后次数不可知）。
> - **口径边界**：reset 前的**全部内容**（回合、关系、记忆）**永久不可恢复**——本估计是"从被删事件反推"，**不是**可加总的台账。

## 5. ⑤ 复核：`user_hash` 不是身份

### 5.1 代码确证
`handlers/hooks.py:1072`：`"user_hash": current_prompt_info["content_hash"]`；
而 `current_prompt_info["content_hash"] = audit_ledger.content_hash(bare_current_prompt)`（同文件 1061 行）——即 **`bare_current_prompt`（清洗后的"本回合玩家输入文本"）的内容哈希**。

### 5.2 实证确证（`llm_audit_index`，2682 条）
- 2682 条记录 → **2599 个不同 `user_hash`**（≈每回合一个，符合"内容哈希"）。
- **`user_hash → user_preview` 是单射**：**0 个** hash 对应 >1 种预览文本。
- **同一 hash 被复用**：`0f2d3abe6a09499d` 出现 **36 次**（同一段开场模板文本被重复触发）→ 相同文本 ⇒ 相同 hash，**与"谁在玩"无关**。

### 5.3 对第一轮附H 的影响
- **事实层面**：第一轮附H 的方法**并未直接把 `user_hash` 当身份键**——它用的是 `provider/model 多样性 + 活跃时间窗 + 会话形态 + 库创建时间` 作代理签名（附H 原文第 394 行）。**因此附H 的结论不因这一字段而作废。**
- **但**：附H 的**标题"用户身份签名"与"无真实设备指纹"的表述会误导**读者以为用了身份字段。**更正要求**：
  1. 附H 的代理签名**不含** `user_hash`，`user_hash` **不含任何身份信息**，**不能**用于区分用户/设备；
  2. 附H 中"开发者 7 provider / 真实玩家 1–4 provider"的分野**仍成立**（基于 provider 字段，非 user_hash）；

## 7. 追加（应 requirement-analyst 请求）· 时钟基线复测：39% → 56.5%

**请求**：把"zone 时间 vs 玩家权威时钟一致率"从 `game_sessions.current_time_slice`(L3) 改到 `get_current_time_slice_for_player`(L1) 重测。

### 7.1 代码确证（四层时钟）
- `advance_scene_time`（`state_machine.py:3528-3551`）：只写 `scenes.time_slice`(L1) + 经 `_sync_world_clock` 写 `game_sessions.max_*`(L2)，**从不写 `current_time_slice`(L3)**。✅ 证实 L3 是滞留的遗留字段。
- `_sync_world_clock`（`3602-3617`）：仅当场景时间**领先**时才更新 `max_*`。
- `get_current_time_slice_for_player`（`3630-3637`）：**L1 优先**（玩家所在活动场景），global(L3) 兜底 → 这才是玩家权威时钟。

### 7.2 ★ 口径修正：比较单元必须是"玩家**当前** zone"，不是"全部 zone"
- 全部 zone（209 个）vs 当前时钟：L4==L3 = **33.5%**、L4==L1 = **26.8%**——**这是错的单元**，因为 zone 是**历史产物**，跨日累积，本就不该等于"当前"时钟。
- **正确单元 = 玩家当前 zone**（`characters.current_local_id` 即 `zones.local_id`，已验证 23/23 命中）× 玩家**自己的**活动场景时钟（`scene_members` + `is_active=1`）。

| 指标（n=23 玩家观测 / 18 会话） | 值 |
|---|---:|
| **L4==L3（当前 zone vs 遗留 current_time_slice）** | **9/23 = 39.1%** ← **精确复现"39%"** |
| **L4==L1（当前 zone vs 玩家权威时钟）** | **13/23 = 56.5%** ← **修正后基线** |
| L1 != L3（玩家权威时钟 vs 遗留字段） | **17/23 = 73.9%**（会话级 13/18 = 72.2%） |

### 7.3 结论
1. **"39%" 复现无误**（= 玩家当前 zone vs L3）。**requirement-analyst 的更正成立且方向正确**：换用 L1 后一致率**从 39.1% 升到 56.5%（+17.4pp）**——旧口径**低估**了 zone 与玩家时钟的贴合度，因为 39% 里混入了大量 **L1/L3 分叉噪声**（L1≠L3 高达 73.9%）。
2. **但修正后仍有 43.5% 的当前 zone 显示错误时间片** → "时间错位"是**真实存在的缺陷**，不是纯口径假象。
3. **结构成因已代码确证**：`zone_tools.py:211-218` 用**移动前**的 `current_scene.time_slice` 物化目标 zone；`:451-457` 才在 `time_cost>0 and location_changed` 时 `advance_scene_time` → **每次 time_cost≥1 的换地点移动，目标 zone 必然盖上旧时间戳**（除非日后重访刷新）。→ 这是**移动路径的确定性产物**，非偶发。
4. **口径边界**：n=23 玩家观测（5 个双人档各贡献 2），**样本小**；且为**终态快照**（非逐回合），只能给"最终状态一致率"，**不能**给"每回合错位率"。置信度：中。
