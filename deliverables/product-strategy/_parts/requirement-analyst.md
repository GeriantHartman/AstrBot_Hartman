## 第 2 部分 · 复杂度诊断

### 2.1 「面向用户的功能面」折算

把 49 工具 + 52 命令 + 94 配置 + 24 技能 + 2 流水线折算成**面向用户的功能点/开关**：

| 维度 | 数量 | 说明 |
|---|---:|---|
| LLM 工具 | 49 | 模型可调用的动作 |
| `/rpg` 子命令 | 52 | 玩家/管理员可输入的动作 |
| 配置开关 | 94 | 部署者可调的旋钮 |
| skill 目录 | 24 | 可加载的叙事技能包 |
| 流水线 | 2 | 两套 turn engine |
| **功能面小计** | **221** | 不含内容资产 |
| 内容资产（非功能） | 28 卡 + 10 preset | 世界/角色内容 |

> **面向用户的功能面总数 ≈ 221 个可交互功能点/开关**（主插件）。再加生态层第二个完整游戏（85 py / 16,124 行）与 3 个附属插件，**"表面积"实际更大**。

### 2.2 其中多少是玩家不可见 / 不可达？

| 类别 | 数量 | 数据依据 | 判定 |
|---|---:|---|---|
| 纯内部记账工具（玩家 0 可见） | ~11 | 占 **65.3%** 调用（3,750/5,743） | ❌ 不可见 |
| 僵尸工具（≤5 次调用） | 12 | 合计仅 33 次 = 0.6% | ❌ 近乎不可达 |
| 历史遗留别名 | 11 | 434 次 / 7.6%（占着统计口径却不该在） | ❌ 冗余 |
| 孤儿映射牵连工具 | 14 | 映射到 6 个**不存在**的技能目录 | ❌ 断裂 |
| 废弃/兼容配置 | 17 | 14 `narrative_review_*` + `enable_auto_install_skills`/`intent_max_retries`/`enable_4_0_contract_pipeline` | ❌ 死开关 |
| 无主技能（真孤儿） | 2 | `rpg-festival`、`rpg-weather`（有目录、无工具映射） | ❌ 不可达 |
| 管理员/调试命令 | ~12 | `npc_*`/`dedup`/`debug`/`config`/`pipeline`/`director`/`tendency` | ❌ 玩家不可达 |

> **结论**：221 个功能面中，**约 60~70 个（≈ 30%）是玩家不可见、不可达、断裂或冗余的**。这正好解释了产品负责人的体感——**"功能多"是表面积，"效果不好"是因为近三分之一的功能根本不产生玩家可感知的体验。**

### 2.3 重复与冗余清单（可逐条清理）

1. **双流水线并存**：4.0 Contract（默认）+ 5.0 Router Supervisor（实验），两套完整 turn engine。**用户不该看到这个选择**（竞析）。
2. **6 个孤儿映射**：`rpg-area-story`、`rpg-mirror-mechanics`、`rpg-story-hook`、`scene-mgmt`、`style`、`memory`——`TOOL_SKILL_MAP`（实测 **49 条**）指向 6 个**目录不存在**的技能，牵连 14 工具。
3. **2 个无主技能**：`rpg-festival`、`rpg-weather`（另有 12 个技能目录未被 map 引用，属"系统内无主"）。
4. **11 个遗留别名**：`update_npc_affinity`(248)、`update_npc_state`(72)、`log_zone_events`(41)、`generate_npc`(18)、`set_companion`(16)、`use_item`(11)、`dismiss_companion`(9)、`execute_combat_round`(8)、`update_npc_relationship`(6)、`update_npc_relationships`(3)、`log_npc_interaction`(2)，合计 **434 次 / 7.6%**。
   - ⚠️ 代码注释自称"Keep this list to current LLM-callable tools only. Legacy aliases belong in the offline analysis skill"——**但统计管线仍在摄入这些别名**，说明"清理"只做了一半。
5. **14 个废弃配置**：`narrative_review_*` 全家族（官方口径 `deprecated_noop_except_generation_abtest`）。
6. **独立 reviewer 插件**：功能已废弃，插件却仍在（3,936 行）。
7. **风格机制重叠**：主插件 `rpg-style-*`（8 skill）+ `astrbot_plugin_style_skills` 独立插件。
8. **镜像系统整条断链**：5~7 个工具全部近乎僵尸（合计 ~36 次），映射指向不存在的技能。

### 2.4 "为架构而架构"的典型证据

| 证据 | 数据 | 为什么是"为架构而架构" |
|---|---|---|
| 双流水线 | 2 套完整 turn engine，仅 1 套默认 | 技术演进（4.0→5.0）的中间态被**永久暴露**，用户承担了迁移成本 |
| 独立 reviewer 子系统 | 3,936 行，已声明废弃仍存活 | **废弃声明 ≠ 物理下线**，架构债沉淀成插件 |
| 94 配置 vs 30 注册 | 缺口 **68.1%** | 有统一注册表**却不强制登记**——"收口机制"本身没有收口 |
| 镜像系统 | 7 工具 → 不存在的技能，~36 次调用 | **先建能力，再找用途**，用途从未出现 |
| 24 skill 独立开关 | `rpg-style-*` 一个系列 8 个 | 风格应是"预设"，被拆成 24 个独立加载项 |
| 契约要求 vs 合规率 | 要求"末尾 3-4 编号选项"，实际 **45%** | 契约是**写给架构看的**，没有后置校验兜底 |
| 统计口径 | 遗留别名仍进统计 | 展示层比运行时"更脏"，说明统计是为**盘点**而非**产品**服务 |

### 2.5 质量债（必须并入地图，不是"功能"但直接毁体验）

| 债务 | 实测 | 对玩家的伤害 |
|---|---|---|
| `<xiaoai_core>` 内部思考块泄露正文 | **25.2%**（37/147 含正文记录） | 玩家直接读到 AI 的元规划文本 → **出戏** |
| 编号选项合规率 | **45%**（66/147） | 契约承诺的"3-4 个选项"**55% 缺席** → 玩家不知下一步 |
| 工具失败率 | **6.6%**（178/2,682） | 摩擦，不致命但累积 |
| `sync_zone_npcs` 失败率 | **60%** | 参数格式 bug（"arrive_npcs 必须是 JSON 数组字符串"） |
| 新手引导 | **1 句话** | 玩家**永远不知道**有掷骰/委托/探索/升级/24 技能 |
| 长档天花板 | 审计 200 行 / 内存 120 回合封顶 | 玩到某长度**必然触顶**，没有"自然结束" |
| 输入输出比 | **1:14**（输入 64 字 / 输出 850 字） | 玩家"读"的时间远大于"玩"的时间 |

> **复杂度负债指数（CDI，引自 data-analyst）≈ 53/100**，主要债务 = **玩家不可见记账** + **2/3 配置失管**。

## 第 3 部分 · 精简方案（核心交付）

### 3.0 设计原则（先立价值观，再谈砍留）

1. **砍"暴露方式"，不砍"能力"**：竞析结论——**复杂度不是原罪，复杂度裸露才是**。SillyTavern 参数比我们多，但把复杂度**外置**；我们把它**内置进 94 个开关**。→ 减法优先做**隐藏/自动化**，而非**删除**。
2. **区分三种动作**：
   - **删除（Delete）**：能力已死/断裂/重复 → 物理移除。
   - **隐藏（Hide）**：能力有价值但玩家/部署者不该看到 → 移出默认路径，收进"高级"。
   - **自动化（Automate）**：能力有价值但**手动必然被冷落** → 改为系统自动触发。
3. **可见性优先于深度**：每个保留的玩家可见功能，**必须能产生玩家读得到的一句话**。
4. **每个 scope 新增必须伴随 scope 移除或时间线延长**（本团队纪律）。

### 3.3 「一键开局」设计：94 个配置 → 1 次选择

**核心思路**：把 94 个开关 + 10 preset + 28 卡 + 24 skill 打包成 **StarterKit（开局预设包）**。

**首次启动只问 1 题**：
> 「你想玩哪种世界？」
> ① 校园日常 ② 冒险委托 ③ 悬疑推理 ④ 恋爱日常 ⑤ 硬核 TRPG ⑥ 自定义（高级）

**每个 StarterKit = 4 件套的推荐值打包**：
```
StarterKit = {
  世界观 preset      (如 honkai3-return.json / genshin.json)
+ 起始角色卡         (从 28 张 canonical 中预选)
+ 风格 skill 组合    (从 rpg-style-* 中预选，替代手动 set_narrative_style)
+ 94 个配置的推荐值  (其余全部走默认，可玩)
}
```

**分层暴露**：
- **默认层（玩家看）**：6 个 StarterKit 选项 + 极简状态条。
- **高级层（折叠）**：94 个配置收进"高级设置"，默认折叠，**默认值必须能玩**（当前最大缺失）。
- **开发者层（不暴露给玩家账号）**：双流水线选择、注册表、审计——呼应 user-researcher"开发/游玩物理分离"。

### 3.4 迁移路径：不破坏现有存档/数据做减法

**原则**：**先"停止新增"，再"隐藏"，最后"删除"**；每一步都保留 1 个版本的回滚窗口。

| 阶段 | 动作 | 存档安全策略 |
|---|---|---|
| **Step 1 · 冻结** | 停止新增工具/配置/技能；新功能需 CDI 增量 ≤ 0（data-analyst 建议的验收闸门） | 无影响 |
| **Step 2 · 收口** | 把 64 个未注册配置强制纳入 `config_switch_registry`；孤儿映射标记为 `deprecated` 但仍可解析 | 配置读取保留"未知键静默忽略" |
| **Step 3 · 别名清理** | 旧工具名 → 规范名映射表（compat 层），打 deprecation 警告，**保留 1 版本** | 存档中的旧引用由 compat 层自动迁移；不物理改名存档字段 |
| **Step 4 · 隐藏** | 双流水线一条、24 skill、记账工具、镜像/光锥等移出默认路径 | 数据表保留，仅停止暴露 |
| **Step 5 · 删除** | 1 版本后：删别名、删孤儿工具、删废弃配置、归档 reviewer 插件 | 删除前**打 git tag**；数据表迁移到 `archive/` 而非 `DROP` |
| **Step 6 · 验证** | 用 CDI + 合规率 + 失败率 + 玩家可见调用占比做验收 | 旧存档可正常读取 = 迁移成功 |

**legacy 别名清理策略（专项）**：
1. 建立 `LEGACY_ALIAS_MAP = {旧名: 新名}`（11 条）。
2. 运行时：若 LLM/prompt 调用旧名 → 自动路由到新名 + 记 1 条 warning。
3. 统计层：**立即**把旧名归并到新名（不再让旧名污染口径）。
4. 1 个版本后：删除 alias map，删除旧名 handler。

## 第 4 部分 · Non-goals（这次明确不做）

> 目的是**防止范围蔓延**——减法方案最容易被"顺手再加一个"毁掉。

1. **不做"新增功能"来解决问题**：本轮只做减法（隐藏/自动化/删除）与暴露层。任何新玩法机制（新武器/新职业/新副本）**一律拒绝**。
2. **不追求"服务 100 个陌生玩家"**：D3 元问题未裁决前，不投入社区/UGC/市场/多用户运营。
3. **不做移动端 / 云托管 / 服务器化**：本轮是本地插件的**内部精简**，不改部署形态。
4. **不做多模态（TTS/图像）**：P2-5 只登记不排期。
5. **不砍"内容型功能"本身**（伏笔/记忆/委托/角色卡）：它们是**留存钩子**，本轮只改**暴露方式**（手动→自动），不删除。
6. **不删 canonical 角色卡 / preset 内容**：内容资产是长板（竞析 S 优势），只做"打包成 StarterKit"，不删内容。
7. **不重写流水线引擎**：只做"二选一 + 隐藏"，不在本轮重构 turn engine。
8. **不碰 NSFW 子系统**：真实用法强相关，保持现状。
9. **不在形态裁决（P2-1）之前删玩法机制层**：形态未定前，只"隐藏"不"删除"。
10. **不做 UI/前端大改**：状态可见层以"文本状态条"实现，不做独立面板（留待后续）。
