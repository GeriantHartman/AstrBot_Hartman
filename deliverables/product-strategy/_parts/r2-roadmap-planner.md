## 2. 三阶段路线图

> **总原则**：**先让仪表说真话（阶段一）→ 再加固直接服务 D5 四要素的核心体验（阶段二，重心）→ 最后让"建造节律"与"消费模式"共存（阶段三）**。
> **Gate 定义纪律**：每条 Gate 必须是**可观测的确定性事件**——配置断言、计数阈值、AST 扫描结果、文件存在性、字段落盘。**禁止**"玩家感觉更好""体验提升"这类不可验证表述。
> **不绑日历**：周期仅为量级参考【推断】，按单人可支配时间推进。

### 2.0 依赖关系

```
阶段一：止血 + 真实可观测 ──┐
（先让仪表说真话）           │  阶段二的所有 Gate 依赖阶段一的埋点/审计
                            ↓
阶段二：核心体验加固 ───────┐  ← 本路线图重心
（只做 D5 四要素）           │  阶段三依赖阶段二验证过的"核心体验 + 观测代理"
                            ↓
阶段三：建造节律 + 消费模式
（让建造与消费共存）
```

### 2.1 阶段一 · 止血与"真实可观测"

> **主题**：**让仪表与状态都反映真实，并修掉直接导致"出戏"的确定性缺陷。**
> **本阶段不碰形态、不做减法、不做增长**。只修"影响玩家"和"支撑后续 Gate"的东西。
> **边界**：区分两类缺陷——**状态缺陷（player-facing，要修）** vs **仪表缺陷（operator，延后）**。无单一时间源（三层时钟）属前者；延迟埋点 / 审计覆盖 / CDI 属后者。

1. **好感度**：存在 **≥ 3 个可区分的中间态**（确定性构造测试：给定 3 个不同好感值，产出 3 个不同的可见后果）；且 **reset / 新群后好感度不自动满值**（状态断言）。

3. **角色还原**：同一角色在 ≥ 20 轮内的**口吻一致性回归**通过（确定性：风格标签漂移次数 ≤ 阈值）。
4. **契约**：**编号选项合规率 ≥ 85%**，且**分 provider 极差 < 20pp**。
5. **建造者回路**：**一局结束后自动产出 ≥ 1 份"高光 / 意外"产出物**（文件存在性断言），且其中 ≥ 1 条为负责人未在开发中预设。
6. （可选）**机制层 26 工具在默认配置下 `enable=false`**（config 断言）。

> **风险总控**：阶段二是核心引擎改动密集区。**任何改动都必须先建回归样本集**（角色一致性 / 口吻 / 好感度状态），否则无法证明"没改坏角色还原度"。

## 4. 替代"流式输出"的方案

### 4.1 先用 B2 重新评估：这个问题的真实优先级

**B2 成本评分（负责人逐字）**：

| 环节 | 成本 |
|---|---|
| 启动产品 | 1 |
| 选角色卡 | 1 |
| **等 LLM 首字** | **1** |
| 读输出 | 1 |
| **想我接下来说什么** | **4** |
| **中途出戏** | **4** |
| 收尾结束 | 3 |

**评估结论**：
> **"等 LLM 首字"只值 1 分——与"启动产品""选角色卡"同级，是最低档。**
> 两个真正的 4 分痛点是"**想我接下来说什么**"（认知劳动）与"**中途出戏**"（沉浸断裂）。
> → **第一轮把"流式输出"列为最高杠杆，是被"每回合等 60 秒"的错误推断撑起来的。**
> → **`move_to_zone` 的 10–28 秒卡顿，作为"等待"问题，优先级 = 低。**（且 P0-8 已实测：全量加权仅 **2.7 秒/回合**，只覆盖 **10.7%** 的回合。）

**但有一个真实的反转**：这个等待**发生在最坏的时点**——
> B4 逐字：「移动到了不同的区域，我该思考在这个区域做什么，时间段切换是否合理，是否有新的角色，新角色出现是否合理，我该如何搭话。」
> 即：**等待与"想我接下来说什么"（4 分）的认知高峰重叠。** 而"死等"期间**玩家看不到新区域，无法开始构思** → 空转，且**无信号 → 读出戏**。

**→ 所以真实问题不是"秒数"，而是两件事**：
- **(a) 死等没有信号 → 被读出戏**（B2 4 分）。
- **(b) 等待挡在玩家最需要信息的构思时刻之前**。

### 4.2 替代方案（按性价比排序）

| # | 方案 | 针对 | 是否确定性 | 成本 | 备注 |
|---|---|---|---|---|---|
| **1** | **可感知的进行信号（legibility）**：生成期间先发一条确定性过渡消息（"世界正在展开…"）或 typing indicator，把"死等"变"有反馈的等" | **(a) 出戏** | ✅ 确定性模板 | 极低 | **最高性价比**——直接打 4 分痛点，不打 1 分痛点 |
| **2** | **两段式输出**：先秒回一段**模板化**场景过渡旁白（非 LLM），再补世界细节 | 首字延迟 | ✅ 确定性 | 低 | 首字等待本就 1 分 → 压到 ~0，长尾放到玩家已在阅读时 |
| **3** | **预生成 + 缓存**：相邻 zone 后台预生成 / 复用 zone 缓存，命中即秒回 | (b) 挡路 | ✅ 确定性 | 中 | 把 10–28s 移出关键路径 |

**本轮结论**：
> **把 `move_to_zone` 从"最高杠杆修复"降为"P1-低"**，只做**方案 1（legibility，极低成本）**，其余按需。
> **明确不做**：任何"让玩家看生成进度条 / 调参 / 手动操作"的方案——违反 C7（玩家不调用工具）。

**Gate（方案 1）**：`move_to_zone` 调用期的占位信号**覆盖率 = 100%**（确定性：每次调用均产生一条过渡消息，日志断言）。
**Gate（方案 3，若做）**：`move_to_zone` 缓存命中率 ≥ 50%，P90 等待 < 3 秒。

### 4.3 ⚠️ "zone 预生成缓存"与"单一时间源"是否冲突？——**会冲突，且时间源收敛是缓存的前提**

> **冲突是真实的**：一个预生成的 zone 若**携带生成时刻的时间戳 / 时间相关描述**，当时间推进后又被命中，就会**在缓存里固化一个过期时间切片**。而当前**三个时间源本就不同步**（S==C 26.1% / C==Z 56.5% / S==Z 39.1%），**在时间源收敛前上缓存，等于在三个不同步的源之间再加一层固化缓存**。
> **代码复核已确认冲突的机制**：`volatile_cache["time_snapshots"]` **不是死代码**，有 2 个活跃读取站点——`workflows/scene_generator.py:282`（`get_or_create_zone` 重访路径）与 `handlers/zone_tools.py:79`（`query_current_zone` 读路径）；且 `scene_generator.py:325` 写入快照的 key 是**调用时传入的 `time_slice`**。→ **"按某个源的时间存、可能用另一个源去命中"的机制真实存在**（`zones.time_slice` 亦为 `state_machine.py:1677-1733` 的派生/缓存字段）。我提议的 zone 预生成缓存若沿用同一模式，只会放大问题。

**解决办法（两者兼容，且互相成就）**：
1. **缓存必须"时间无关"（time-agnostic）**：缓存只存**空间层内容**（区域布局 / NPC 名册 / 描述骨架），**不存当前时间**。
2. **时间层在"服务时刻"从唯一权威时间源渲染**：玩家请求进入 zone 时，才把权威时间（早晨 / 夜晚…）叠加到缓存的骨架描述上。→ 缓存永不烘焙时间戳，**过期策略与时间源解耦**。
3. **失效策略**：时间无关的骨架 → **按内容失效**（NPC 名册变化 / 剧情推进），**不按时间失效**。只有"时间层渲染"是每次现算（成本极低，是模板拼接，不是 LLM 调用）。
4. **依赖关系**：**"确立单一时间源"是"zone 预生成缓存"的前置依赖**（§3.2 已注明）。顺序必须是 **先收敛时间源 → 再上缓存**。**没有单一时间源，缓存就没有可靠的 key**——这是比"给缓存加失效策略"更根本的理由。
   - **⚠️ 新增前置（主理人+析客取证）**：在 **`get_time_info()`（`state_machine.py:2631`）改为 scene-aware 之前**，缓存会把 **L3 僵尸字段的冻结值固化进 LLM 上下文**（该函数 docstring 写着"for LLM context injection"，却裸读 `gs.get("current_time_slice","")`，13 调用点 / 5 处注入 LLM）。→ **施工顺序：① 改 `get_time_info()` → ② 清 `current_time_slice` 读取点 → ③ 修 `move_to_zone` 顺序 → ④ 才上缓存。**

> **一句话**：**收敛时间源消除"zone 自带时间"这个冗余字段，正好让 zone 内容变得可安全缓存。** 二者不是冲突，是**"先修物理法则，再修传送门"**的先后关系。
> **反向收益**：若析客裁决"删除 `zones.time_slice` / `scenes.time_slice` 的独立写路径，时间只保留一个权威源"，则**缓存的不一致风险从结构上归零**。

### 5.1 诊断：**创造者悖论**

| 开放问题 4：「如果永远只有一个玩家，还会继续维护——会」 | 维护意愿不依赖玩家数。 |
| A6 / 开放问题 1：「投入到别的工程和项目中，且感觉到**没有新鲜感**」 | 停玩 = **新鲜感耗尽**，不是产品坏了。 |
| B7：「自动代码搬迁到服务器后，没有更新过功能。但我也没怎么玩」 | **玩与建造同频**：停止更新 → 停止游玩。 |
| 数据：12 会话 / 1915 回合 = **49%** | 他**不是不玩**，是**建造冲刺期集中玩**。 |

> **一句话**：**他是一个"以建造为奖励、以新鲜感为燃料"的人；而建造会消耗新鲜感。这不是缺陷，是一个必须被设计承接的张力。**

### 5.2 三个机制建议

#### 建议 A · 把"意外感"变成可交付的产出物（Externalize surprise）

- **机制**：每局 / 每周**自动**从审计台账生成一份**"意外回放 / 高光卡"**——列出玩家未预设、由 **NPC 主动产生**的台词与事件（对应开放问题 3「被 NPC 意外到」）。
- **为什么有效**：把"新鲜感"从"需要他亲身沉浸才能获得"（已被开发破坏）转成"**他造的系统产出的、连他自己也没预料到的内容**"。→ **建造者也能收到意外。**
- **合规**：产出物由系统自动生成，**不需要玩家操作工具**（合规 C7）。
- **实现**：从审计提取 NPC 台词 + 玩家正向回应代理（§6 代理 A / D），自动成卡。
- **Gate**：一局结束后自动产出 **≥ 1 份高光卡**，且其中 **≥ 1 条为他未在开发中预设**。

#### 建议 B · 为建造者设计专门的回路（Builder loop）

- **承认"建造"和"游玩"是两个不同回路**：

| 回路 | 循环 | 奖励性质 |
|---|---|---|
| **建造回路** | 新卡 / 新机制 → 发布 → **游玩验证** → 看到效果 | **即时、确定**（他本来就强） |
| **游玩回路** | 消费 → 被意外 → 关系发展 | 延迟、不确定 |

- **机制**：把"**发版**"设为**建造回路的终点 + 游玩回路的起点**——发版后进入一次"**验收游玩**"（≥ 20 分钟，期间禁入开发环境）。它既是质量门，也是他被世界拉进去的窗口。
- **为什么比第一轮"先玩后改"更好**：第一轮把它当"行为矫正"（暗示他有问题）；本轮把它**嵌进他本来就高频的建造节律**——**不要求他改变节奏，只要求他在既有节奏上多走一步**。
- **Gate**：每次发版记录 **≥ 1 次验收游玩会话**。

#### 建议 C · 承认并接受"建造期玩得多、维护期玩得少"是正常节律

- **数据佐证**：停玩与"停止更新功能"同步（B7）→ **玩与建造同频**，是**节律**而非**衰退**。
- **因此**：
  1. **不设"每日 / 每周留存"目标**（违反前提 4，且会把正常节律误判为失败）。
  2. **路线图按"建造节律"排期**：建造冲刺 → 验收游玩 → 维护低玩（正常）→ 下一次冲刺。
  3. **产品侧只需保证一件事**：**"每次他想玩时，进入成本接近零"**（一键继续 + 自动"上回说到"），而**不是"逼他常来"**。
- **Gate**：**不设留存目标**；只设"进入摩擦"事件（一键继续可用、开场自动生成——确定性断言）。

#### 建议 D（可选）· 外部注入新鲜感

- 少数朋友玩出的剧情 / 卡 / 高光**回流**给负责人（阶段三）。**这不是增长，是"给一个建造者提供他自己没造过的东西"。**

> **诚实提醒（对本人的一击）**：他 M1 说"更在乎做产品的 KPI"，开放问题 4 说"永远一个玩家也会维护"。→ **本轮路线图不以"让他多玩"为目标**——那会重蹈第一轮"行为矫正"的覆辙。**目标只有一个：当他决定要玩时，产品配得上他的那 20 分钟。**

## 6. 成功标准重构：如何观测 M1 的定性北极星

### 6.1 北极星（M1 逐字）

> **「能否听到用户说'哇，我好喜欢这个角色说的话'」**

这是**定性指标**。第一轮的"单次愉悦度"需要自评 → **违反"不设计问卷打扰"**；"主动打开频率"是增长类 → **违反前提 4**。**两者均作废。**

### 6.2 观测设计：确定性行为代理（不打扰、不问卷、不让玩家操作）

> **纪律**：以下代理是**玩家行为的观测遥测**，**不是叙事质量门禁**。它们只做**确定性的文本存在性 / 长度 / 计数检测**（不判断叙事好坏），且**每周由负责人人工读一份摘要**——符合 `AGENTS.md` 第 10 条（代码不做非确定性叙事判断）。

| 代理 | 定义（确定性） | 对应 M1 的哪句话 | 数据源 |
|---|---|---|---|
| **A · 引用回声** | 玩家本轮输入是否包含**上一轮 NPC 台词的逐字片段（≥ 4-gram）**或该 **NPC 专有名词** | "**我好喜欢这个角色说的话**"——他把这句话**引用回来了** | 世界库玩家输入 + 审计 `assistant_preview` |
| **B · 正向延续** | NPC 台词后，玩家下一轮输入长度 **≥ 该玩家该档中位数**，且**继续围绕同一 NPC** | "喜欢"→ **愿意继续投入**（行为的"喜欢"，不是嘴上说的） | 世界库 |
| **C · 主动回访** | 玩家**主动开新 session 并直接找某 NPC**（无外部提示） | A5 #1「**单纯想和某个 npc 说说话**」 | `game_sessions` + 首轮输入 |
| **D · 自由越轨** | 玩家对 NPC **主动发起的事件**做出**非编号选项的自由文本回应** | 开放问题 3「**被 NPC 意外到**」；E3「想要新鲜感和意外感」 | 审计 + 世界库 |
| **E · 状态回溯率**（诊断代理，**非北极星**） | **双口径**：①（直接指纹）**`visible_events` 的 AUTOINCREMENT 水位 > 现存行数 = 发生过 `/rpg reset`**（该表只增不删，唯一删除路径是 `wipe_session`）；②（幅度）`max_time_index − time_slice_index` / `max_day_count − day_count` 高水位差 | **"状态可信度"的天然代理**——开放问题 5「我几乎没有控制权，只有 reset\forget」。实测：**5 个会话命中直接指纹，合计抹除 367 条 visible_events**；`FriendMessage:245432630`（ic 仅 12）**曾插入 233 条 visible_events / 504 条 npc_events**（现仅存 6 / 5）→ **reset 幅度极大（数百回合一次清零）** | `visible_events` 水位 + `game_sessions` 高水位列 |

**关于代理 E（`reset` / `forget`）——必须谨慎，不能当目标**：
- **它是诊断代理，不是北极星，也不是"越低越好"的目标。** `reset` 是负责人**唯一的控制杠杆**（开放问题 5），因此它**可能是正常使用**，也可能是**状态不信任**——**单看频率无法区分**。
- **双口径互补**：`visible_events` 水位给出**"是否发生过 reset + 抹除幅度"**（比 `max_*` 更直接、更硬）；`max_*` 高水位差给出**"回退幅度"**。两者并列观测。
- **行为签名不同，不可混为一谈**：`FriendMessage:245432630` 是**极大幅度、一次性清零**（数百回合），与"频繁小幅回溯"是**完全不同的行为**——前者像"推翻重来"，后者像"微调重选"。**分析时须按幅度分层，不要只看总次数。**
- **正确的用法是"配对观测"**：把 E 与**单一时间源**修复配对——
  - 若**时间源收敛后 E 显著下降** → 证据链成立：**回溯主要是他修正状态不自洽的手段**（主理人 §5.3 假设被验证）。
  - 若**时间源收敛后 E 不变** → 回溯是**风格性使用**（他享受"重选"本身），不应干预。
- **数据依赖**：由数析验证"回溯是否集中发生在时间源冲突之后"（`r2-00` §5.4 待办）。
- **Gate**：阶段一后**可查询**"单位回合 reset/forget 次数 + 抹除幅度"（确定性字段落盘）——**不设数值目标**。
- **顺带修正回合口径**：数析据 reset 指纹把**真实累计回合上修为约 4,800–5,800**（3931 为严格下限）→ 本报告凡引"3931"处，均应读作**下限**。

### 6.3 北极星读数与 Gate

- **北极星观测 = 以上代理的"周频次 + 覆盖角色数"**（不是均分、不是留存率）。
- **Gate（阶段二起）**：**代理 A + B 在某一角色上出现 ≥ N 次 / 周** → 视为"**听到了那句话**"的行为证据。（N 由负责人首周基线自定。）

  - **不新增 LLM 工具 / 配置**（防止范围蔓延）。
- **明确弃用**：主动打开频率 / DAU / 留存率 / 回合数**均不作目标**。回合数仅作"承载力参考"（单档 1062 为基线【实测】）。
- **同样不作目标**：`reset` / `forget` 频率（代理 E）——**只作配对诊断**，不设"降低到 X 次"的目标。

### 8.1 单一时间源 Gate 判据与 X 的取值依据

> **问**：一致率 ≥ X%，X 取多少？
> **答**：**这个 Gate 不应是一个"百分比阈值"，而应是一条"不变量"**——因为阈值化等于"接受一部分状态在撒谎"，这对状态字段是不自洽的。
> **口径更正（主理人三层全量普查后，最终版）**：时间有**三个独立可写源**——`game_sessions.current_time_slice`（会话级单值，`database.py:135`）/ `scenes.time_slice`（场景级）/ `zones.time_slice`（派生/缓存，`state_machine.py:1677-1733`）。`move_to_zone` **优先读 `scenes.time_slice`**（`zone_tools.py:211-218`），`game_sessions` 只是兜底。→ **缺陷的根因不是"某个字段落后"，而是"没有权威时间源"。** 精确口径改为**三层两两一致率**（23 个 session×player，`lead_three_clock2.py`）：

```
S(game_sessions.current_time_slice) == C(scenes.time_slice) :  6/23 = 26.1%
C(scenes.time_slice)                == Z(zones.time_slice)  : 13/23 = 56.5%
S(session)                          == Z(zone)              :  9/23 = 39.1%
scene.local_id == player.current_local_id                   : 23/23 = 100.0%   ← 入口对得上，时间对不上
```

**不变量 A'（必做，与语义无关）**：

| 判据 | 依据 |
|---|---|
| **任一时刻、任一玩家，`scenes.time_slice` / `zones.time_slice` / `game_sessions.current_time_slice` 必须表达同一时间切片，一致率 = 100%** | **玩家正在读它们。** "**站在深夜公寓里而世界是早晨**"是**体验问题**（B4「时间段切换是否合理」）。与缓存语义无关，因此必须单列。**最刺眼证据**：`GroupMessage:966162158` 同群同刻，「技术支持——哈吉博」S=早晨/C=深夜/Z=深夜（**分裂**）而「墨」S=C=Z=早晨（**全一致**）——**会话级单值在结构上无法表达多玩家各自场景时间**；`GroupMessage:1097436019` 同时存在 **4 个**时间值。 |

**不变量 B（时间源收敛后，按析客裁决的语义，二选一）**：

| 语义 | Gate 判据 | **依据（X 为什么是这个值）** |
|---|---|---|
| **zone/scene 反映"当前时间"**（冗余派生字段） | **等于权威源，一致率 = 100%** | **派生不变量必须精确。** 派生字段的值完全由源字段决定，出现任何不一致都意味着**存在漏改的写路径**（bug），而非"可接受的统计误差"。**因此 X = 100%，不是 90%。** |
| **zone 记录"上次到访时间"**（历史事实） | **0 个值 > 权威源**（无"未来"时间），且 `≤ 权威源` | **历史事实可以落后于当前，但绝不能超前。** "落后"是正常语义（你上次来是早晨，现在是夜晚）；"超前"是逻辑不可能。**因此判据是"0 个越界"，不是百分比。** |

**不变量 C（reset 回滚，共同）**：

| 判据 | 依据 |
|---|---|
| 完整不回溯的一局后 **`max_time_index == time_slice_index`**；任何回退**必须对应一条可审计的 reset 事件** | 高水位与当前值的差 = 回退幅度。无 reset 事件却出现差值 = **未解释的状态回退**（数据损坏）。直接指纹见 §6.2 代理 E（`visible_events` 水位 > 现存行数）。 |

- **当前基线（三层全量普查）**：**S==C 26.1% / C==Z 56.5% / S==Z 39.1%** → **目标：三层全部 100%（不变量 A'）**。
  - **【终稿口径以主理人装配为准】** 主理人终稿收窄为：**不变量 A'（唯一）= `zones.time_slice`（该 scene 绑定的 zone）== `scenes.time_slice`（该玩家成员 scene），基线 56.5% → 100%**；僵尸字段 `current_time_slice` 改用**结构性布尔 Gate**（业务读取点已清零）。**以上方三层全量数字仅作诊断背景。**
- **根因是结构性的，不是配置问题**：`game_sessions.current_time_slice` 是**会话级单值**，而时间实际是 **scene 级** → **单值结构无法表达多玩家各自的场景时间**（`966162158` 一人分裂一人自洽即为证）。→ 修复方向是**收敛为单一权威时间源**（会话级单值需让位给场景级）。
- **冗余字段是"可删除候选"**：`zones.time_slice` 既然是派生/缓存字段，**删除它即可从结构上消除一层不一致**。是否删除取决于析客的时间源裁决。
- **反例（不要这样做）**：设"一致率 ≥ 90%"——它无法回答"那 10% 不一致的状态该不该被玩家看见"，等于把 bug 变成配额。

### 8.2 无单一时间源（三层时钟）vs 好感度二极管：**补充，不取代**

| | 无单一时间源（三层时钟） | 好感度二极管 |
|---|---|---|
| **缺陷层级** | **状态层**（世界的物理法则不自洽；**结构性**） | **情感层**（关系引擎的输出被压平） |
| **影响的 CEP** | CEP5 角色还原 / CEP6 出戏 / CEP7 移动探索 | CEP3 交流陪伴 / CEP6 出戏 |
| **确定性** | ✅ **高**（三层一致率由全量普查直接观测，代码可修，不涉叙事判断） | ⚠️ 中（需设计改造，风险较高） |
| **对应自述** | B4「时间段切换是否合理」；开放问题 5（reset，见代理 E 双口径） | C6 逐字（二极管）；C3 好感度 6 分；C1 心疼 #2 |
| **执行顺序** | **先做**（确定性 + 是 zone 缓存的前置依赖） | **后做**（需先建回归样本集） |

> **结论**：**两者服务于不同的 CEP，互不替代，均入 P0。**
> 但**顺序上，单一时间源先于好感度**——因为①它是确定性的、风险低；②它是 `move_to_zone` 缓存的前置依赖（§4.3）；③它可能**消解掉大量 reset 依赖**，从而**减少"状态不可信"对情感体验的间接伤害**。**先修物理法则，再修情感引擎。**
