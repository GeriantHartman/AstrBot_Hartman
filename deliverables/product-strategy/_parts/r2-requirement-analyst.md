## 0. 本轮规范：什么算「改代码」、什么算「改 prompt/契约/guidance」

本项目已有一条硬规范（约束 5）：**代码只处理确定性事件**（工具调用、状态写入、配置分支、审计落账、模板装配）。因此本报告每条需求都标注施工面：

| 施工面 | 允许做的事 | 禁止做的事 |
|---|---|---|
| **改代码** | 状态读写、阈值/门槛的算术、模板装配、输出后置剥离已知标记、工具名归一化、审计落账 | 用正则/关键词/Verifier/分类器**判断叙事质量或关系是否深化** |
| **改 prompt** | 角色契约、行为指引、场景上下文、语气/称呼规则 | — |
| **改契约** | 工具调用契约、输出格式契约（如"末尾编号选项"） | — |
| **改 guidance / skill** | 阶段行为集、风格包、里程碑清单 | — |
| **改配置** | 默认值、开关、StarterKit 打包 | — |

> **一句话原则**：**"差异"必须由状态（确定性）驱动，而不是由代码"判断"驱动。** 代码负责"当状态 X 时注入契约 Y"，不负责"读文本判断关系够不够深"。

## ① 用 D1 定义唯一核心循环

### 1.1 D1 原始旅程（亲述，逐字）

> 1. 进入世界后，探索世界 → 2. 遇到喜欢的角色 → 3. 与喜欢的角色深入交流发展关系 → 4. 意外情况下偶遇其他的喜欢的角色 → 5. 与更多的角色建立关系

**关键观察**：这是一条**叙事弧（arc）**，不是循环（loop）——它单向、有终点（"与更多角色建立关系"之后呢？没有第 6 步）。**而且它内部没有任何机制**：没有一个词提到战斗、成长、委托、掷骰、光锥、奖励。这是一条**纯关系消费弧**。

### 1.2 把它写成唯一核心循环

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
   [探索世界] ──► [遇见角色] ──► [交流 / 发展关系] ──► [关系深化]
        ▲              ▲                                    │
        │              │                                    ▼
        │         [偶遇更多角色]  ◄────────────  [解锁新内容]
        │              │                     （新台词/新事件/
        │              │                       新角色/新情境）
        └──────────────┴────────────────────────────────────┘
```

**核心循环（关系消费循环 / Relationship-Consumption Loop）**：
> **探索世界 → 遇见角色 → 交流并发展关系 → 关系深化解锁新内容（新台词/新事件/新角色）→ 新内容驱动再探索 → 偶遇更多角色……**

- **引擎（engine）**：关系深化。
- **燃料（fuel）**：关系深化**必须产出新的可消费内容**。
- **回报（reward）**：情感价值——具体化为 M1 的北极星句「哇，我好喜欢这个角色说的话」。
- **终止条件**：**无**。循环可持续，因为关系可深化到新角色、新角色又带来新关系。

### 1.3 当前产品的循环在哪里断了【核心诊断】

用 D1 对照现有 49 个 LLM 工具（`handlers/_base.py:36-86` 的 `TOOL_SKILL_MAP`，共 49 条）：

| D1 步骤 | 由谁承担 | 健康度 |
|---|---|---|
| 探索世界 | `move_to_zone`(420)、`query_current_zone`(45)、`inspect_environment`(17)、`set_time_slice`(25)、`create_area` | ✅ 健康、可见 |
| 遇见角色 | `generate_npcs`(117)、`sync_zone_npcs`(208) | ⚠️ 可见，但 `sync_zone_npcs` 60% 失败 |
| **交流 / 发展关系** | `update_npc_affinities`(**969**)、`log_npc_interactions`(**984**)、`mark_interacting_npcs`(396)、`unmark_interacting_npcs`(226)、`mark_npc_evolution_trigger`(570)、`set/dismiss_companions`(72)、`recall_npc_history`(5)、`recall_memory`(1) | ❌ **玩家 0 可见**——关系只写进数据库，不产出任何玩家读得到的东西 |
| **关系深化 → 解锁新内容** | **（无）** | ❌ **完全缺失**——没有任何工具把"关系变深"转成"新内容" |
| 偶遇更多角色 | **（无专用机制）** | ❌ **完全缺失**——"意外偶遇"只依赖 LLM 自己想起来，无机制保障 |

> **断裂点**：循环的**引擎边缘**（"关系深化 → 解锁新内容"）在代码里**不存在**。关系深化的全部产物是数据库里的一个整数（`npc_player_affinity.value`），它既不可见、也不解锁任何东西。**这就是为什么"关系"体验会塌缩成"二极管"（见 ③）——因为循环只有一个死端点。**

## ② 用 M1 的产品 KPI 反推需求优先级

### 2.1 M1 原话与北极星

> **做产品 KPI**：能否还原角色；能否让用户感受到角色是鲜活的有个性的；能否带给玩家良好的用户体验和情感价值；**能否听到用户说"哇，我好喜欢这个角色说的话"**
> 玩游戏的 KPI：能否和角色好好相处；能否识别出角色的出戏感；能否想出新的剧情
> **我更在乎做产品的 KPI**

**北极星（定性）**：**"哇，我好喜欢这个角色说的话"**

> 这条 KPI 是**逐句质量型**（quality-per-utterance），不是**留存/规模型**（quantity）。它衡量的是"某一句台词是否击中人"，而不是"玩家玩了多少小时"。**这一条就否决了所有"耐玩/平衡/难度曲线/DAU"式需求。**

### 2.2 什么样的功能改动能让这句话更可能出现？（可施工清单）

把北极星句拆成 6 个必要条件，逐条给施工面：

| # | 让这句话出现的条件 | 施工手段 | 施工面 | 现状 |
|---|---|---|---|---|
| **N1** | 角色**说得像 TA**（还原度） | canonical 卡 + 角色契约（人设/性格标签/`speech_pattern`）注入 | 改 prompt/契约 | ✅ 已有（`character_director.py` 注入 profile/tags） |
| **N2** | 角色说得**出人意料但合理**（鲜活） | NPC 的 `goal`/`wants`/`secret`/`mood` 注入 + **NPC 主动性**（会主动出手） | 改 prompt/契约 | ⚠️ 字段已注入，但**无主动性机制** |
| **N3** | 角色说的是**只有对"我"才会说的话**（关系独特性） | **阶段行为契约 + 关系里程碑**（见 ③） | 改 guidance/契约 + 改代码（状态） | ❌ 缺失 |
| **N4** | 角色**记得我们之间的事**（连续性） | 记忆自动注入 + NPC 视角记忆 + 里程碑记忆锚点（见 ⑤） | 改代码 + 改 prompt | ❌ 近乎缺失（`recall_memory` 仅 1 次） |
| **N5** | 台词**本身好**（文笔/氛围） | style skill + 场景上下文（地点/时间/在场/正在发生） | 改 prompt/skill | ⚠️ 有 style，但场景锚点弱 |
| **N6** | **不出戏**（不被破坏） | 修 `<xiaoai_core>` 泄漏、修契约矛盾、剥离元规划文本 | 改代码（确定性剥离）+ 改契约 | ❌ 泄漏 7.6%、编号选项合规 44.9% |

> **需求优先级规则（由此推出）**：
> **一条改动若不能让 N1–N6 中任意一条更容易发生，就不是 P0——无论它在工程上多"整洁"。**

### 2.3 处理张力：他说"更在乎做产品的 KPI"而非"玩游戏的 KPI"

这句话对需求优先级的三个直接含义：

1. **降级"玩游戏 KPI"驱动的功能**。玩法机制层（战斗/成长/委托/奖励/光锥，~26 工具）服务的是"玩游戏 KPI"（好好相处/出新剧情）。既然他更在乎产品 KPI，**这一层不产生北极星句，应降级/隐藏，而不是投入**。→ 直接支撑需求池 R16。
2. **优先级 = "每一句更好" > "玩得更久"**。产品 KPI 是质量型。因此排序时，**"修出戏"（N6）和"关系独特性"（N3）优先于"加新玩法"**——因为它们直接提升单句质量。
3. **"产品 KPI"与 D3（只服务 1 人 + 少数朋友）自洽**：质量型 KPI 不需要用户量，只需要"他自己被角色打动"。→ 一切增长/留存/规模化需求作废。

### 2.4 张力裁决：产品 KPI 究竟为谁而做？（team-lead 裁定）

我原本提出的张力是：A6 / 开放 Q1 显示他**已经不怎么玩了**，燃料是"建造"而非"游玩"（`r2-00` §3.2）。那么"产品 KPI"（角色还原/鲜活/一句好台词）**究竟为谁而做？**

**team-lead 裁定：产品 KPI 是为他自己——但这不是问题，而是这个产品成立的前提。**

理由：
1. 他 M1 逐字说「**我更在乎做产品的 KPI**」；D3 说「只服务我一个人」；开放问题 4 说「永远只有一个玩家也会继续维护——**会**」。
2. 因此 **M1 的北极星（"能否听到用户说『哇，我好喜欢这个角色说的话』"）不是增长指标，而是他衡量自己造物质量的标尺**。他要的不是 DAU，是**"我造出了一个能让真人说出那句话的东西"**。
3. **所以需求优先级应按"能否让那句话更可能出现"排序，而不是按"哪个玩家用的多"。**

**这一裁定对需求优先级的具体含义（已落实到 §7）**：
- **C6（好感度二极管）升为最高优先级之一**——它直接压制"关系变化的可感知性"，而"角色鲜活"是那句话的前提。→ R1、R3–R6。
- **记忆召回（C3=7 最高）独立成线**——角色能记得你，是"陪伴体验"的核心，也是那句话最可能的触发点。→ R7–R8、R13。
- **工程整洁类（延迟埋点/审计 stage）不应占他的时间**——它们不产生那句话。→ 排 P2（R17–R19）。
- **唯一例外**：`<xiaoai_core>` 泄漏（见 §4.3）直接造成 B2 里 4 分的"中途出戏"，**是"那句话"的直接杀手**，因此保留 P0。→ R2（上下文通道）、R20（展示通道）。

## ③ C6 好感度二极管：具体机制改造方案

### 3.1 C6 原话拆解

> 很容易进入二极管状态，即，最高好感或最低好感（或负好感）才会有明显区别，**中间状态几乎看不出区别**。且后续玩家都喜欢**默认保持自己喜欢的角色在最高好感状态**，即使是 reset、开了新群后也是如此。**不喜欢反复攻略。**

三个子问题：
- **P-A 中间态无差异**：40–59「信赖」和 60–79「亲密」在体验上一样。
- **P-B 默认顶满**：玩家/LLM 默认把喜欢的角色拉到最高。
- **P-C 讨厌反复攻略**：重复"刷好感"没有新内容。

### 3.2 根因（本轮代码核对，全部确定性）

| # | 根因 | 代码证据 | 后果 |
|---|---|---|---|
| **G1** | 好感度注入 prompt 的**唯一信号**是 `好感值 N / 阶段 X` | `handlers/character_director.py:166` `## TA 对玩家「{player_name}」的好感\n好感值 {affinity_value} / 阶段 {affinity_stage}` | 中间态（同阶段内）**注入文本完全相同** → LLM 无任何依据区分 |
| **G2** | 唯一的"差异提示"机制**三重死代码**（team-lead 已独立复核确认） | 见 §3.2.1 | **阶段变化的提示在产品历史上从未执行过一次** → 连"跨阶段"都没差异 |
| **G3** | 阶段阈值是**7 段粗分**，每段 20 分 | `core/models.py:590-605` `compute_stage`：-20/0/20/40/60/80 | 20 分内的所有变化在体验上不可区分 |
| **G4** | 顶满**无成本、无递减** | `npc_tools.py:721` `new_global_val = max(-100, min(100, old_val + delta))`，无收益递减 | LLM 顺手 `+delta` 就顶到 100（P-B 的机制成因） |
| **G5** | "最高好感"是**可继承的默认** | reset 走 `wipe_session`（`commands.py:955`）；但 NPC 是 canonical 角色，其**默认性情**不随 session 改变；`enable_shared_npc_affinity` 让好感跨玩家共享 | 新群/新档里，NPC 仍以"熟悉"姿态出现（P-B 的体验成因） |
| **G6** | 关系深化**不产出任何新内容** | 见 ① 1.3：无"关系→内容"工具 | 深化=纯数值累加 → 必然"反复攻略"且无意义（P-C 的成因） |

#### 3.2.1 G2 的三重死代码（team-lead 复核确认，比初判更严重）

`narrative_package.py:1500-1508` 这段"把阶段变化翻译成叙事行为提示"的逻辑，**在产品历史上从未执行过一次**，原因是**三重叠加**：

| # | 问题 | 证据（本轮复核） |
|---|---|---|
| ① | **工具名用遗留单数** | 该处检查 `entry.tool == "update_npc_affinity"`；canonical 是 **`update_npc_affinities`**（复数，`main.py:1026` 的 `@filter.llm_tool` + `_base.py` 的 `TOOL_SKILL_MAP`） |
| ② | **`stage_changed` 无生产者** | `grep -rn "stage_changed" --include=*.py .` → **全库仅 1 处，即该读取点**，无任何写入 |
| ③ | **`old_stage`/`new_stage` 不在返回结构** | `_apply_affinity_for_npc`（`npc_tools.py`）的返回 dict 只有 `stage`，**没有 `old_stage`/`new_stage`/`stage_changed`** |

→ **结论**：好感度变化时，**唯一改变的是 DB 里的数字**，叙事层从未被告知"态度阶段变了"。这就是 C6 的精确根因。

#### 3.2.2 同源遗留命名的连带影响（同一 bug 的其他受害点）

"`update_npc_affinity`（单数）vs `update_npc_affinities`（复数）"的命名错位**不止一处**，导致多个机制对 canonical 工具**静默失效**：

| 位置 | 内容 | 失效后果 |
|---|---|---|
| `handlers/narrative_package.py:175` | `OPERATIONAL` 集合含 `"update_npc_affinity"`（单数） | `update_npc_affinities` **不在集合内** → 走错处理分支 |
| `handlers/intent_supervisor.py:47` | `_NUMERIC_CLAMPS = {("update_npc_affinity","delta"): (-25,25)}` | **±25 的 delta 钳制对 canonical 工具不生效**（LLM 可提交 +1000，见 `intent_supervisor.py:17` 的注释本身就是这个意图） |
| `handlers/intent_supervisor.py:123` | `if name == "update_npc_affinity":` | 同上，单数匹配失效 |
| `handlers/tool_executor.py:164` | `"update_npc_affinity": {"min_interval_turns": 3, "mode": "accumulate"}` | **最小间隔节流对 canonical 工具不生效** → 好感度可被高频刷（正是 C6「反复攻略」的机制放大器） |

> **这是本轮一个额外发现**：`tool_executor.py:164` 的节流失效，说明"反复攻略"不只是叙事问题，**也是一个被 bug 放大的机制问题**——LLM 可以在同一回合反复 `+delta` 而无节流。

> **修法边界（合规声明，team-lead 要求写入）**：
> - 补 `old_stage`/`new_stage`/`stage_changed` = **纯状态比较**（确定性事件，**合规**）。
> - 统一工具名 = **配置/映射修正**（**合规**）。
> - 保留 `add_behavior_hint` 的措辞"请在 NPC 的表情/语气/行为中自然体现" = **给 LLM 的意图**（**合规**）。
> - ⚠️ **不要**加任何"检查叙事是否真的体现了变化"的代码——那才是**不合规的叙事质量判定**（约束 5）。

> **一句话根因**：**"关系"被建模成一个孤立的整数，且这个整数唯一的作用是往 prompt 里塞一个几乎不变的标签。** 它不是"二极管"，它是"一个没有中段的开关"——**而且连"开关翻转"都没接线**。

### 3.3 改造方案（确定性机制，禁止叙事质量正则）

**设计总原则**：**把"关系深度"从「一个数」改为「一组状态驱动的可观测差异」**。差异来自**状态位**，不来自代码判断。

#### M-A · 阶段行为契约（改 guidance/契约，非改代码）—— 解决 P-A 的一半

为 7 个阶段各写一份**确定性行为契约**（写进 guidance/skill，不写进代码判断）。契约规定该阶段 NPC 的**可执行行为集**：

| 阶段 | 主动行为 | 信息开放度 | 称呼 | 可发起的事件类型 |
|---|---|---|---|---|
| 敌对 / 厌恶 | 拒绝、回避、警告 | 0 | 疏离 | 冲突、驱逐 |
| 陌生 | **只回应，不主动** | 仅公开 | 全名 | 无 |
| 友善 | 主动问候、分享日常 | 日常 | 全名 | 闲聊、带路 |
| 信赖 | 主动求助、倾诉 | 部分 `goal` | 昵称 | 请求帮助、分享心事 |
| 亲密 | 主动邀约、独占式互动 | `secret` 的一部分 | 专属称呼 | 邀约、并肩 |
| 誓约 | 为你承担风险、因你改变目标 | 深度秘密 | 专属 | 承诺、牺牲 |

> **为什么这是"状态驱动"**：阶段是状态（代码写入），行为契约是"按阶段查表"（确定性映射），**不判断叙事质量**。LLM 在 prompt 里拿到"当前阶段→允许的行为集"，自然产出不同行为。

#### M-B · 关系里程碑（改代码 + 改契约）—— 反二极管的核心，同时解决 P-C

**把"关系深化"从「数值累加」改为「离散里程碑的解锁」。**

- 每个 NPC 有一组**关系里程碑**（状态位 0/1），例如：
  `first_name_call`（第一次叫你名字）、`first_secret`（第一次分享秘密）、`first_quarrel`（第一次争执）、`first_reconcile`（第一次和好）、`first_promise`（第一次承诺）、`first_rescue`（第一次相救）、`first_vulnerability`（第一次示弱）……
- **写入方式**：扩展现有 `update_npc_affinities` 的返回/入参，或新增一个 `mark_relationship_milestone(npc, milestone_id)`（**确定性状态写入，代码只记 0→1，不判断质量**）。
- **解锁时注入行为提示**（确定性事件：状态位 0→1 → `narrative_package` 注入一条 `behavior_hint`）。这正是 G2 想做的事，但用**可靠的状态位**而非失效的 `stage_changed`。
- **为什么解决 P-A**：中间态的差异 = "解锁了哪些里程碑"。每解锁一个是**可感知的、一次性的**。
- **为什么解决 P-C（不喜欢反复攻略）**：**里程碑只能拿一次。** 反复攻略一个已满里程碑的角色，**无新里程碑可拿 → 无新内容 → 机制上自然没有"刷"的动机**。这是最优雅的反"反复攻略"设计：不是惩罚刷，而是让刷**没有奖励**。

#### M-C · 誓约门槛（改代码，确定性）—— 解决 P-B

- **进入「誓约」需要同时满足：`value ≥ 80` 且 `已解锁里程碑数 ≥ N`（如 N=4）**。这是纯算术门槛（确定性）。
- 效果：**最高好感不再是"刷数值"能到的**，必须经历事件。LLM 无法"顺手顶满"。
- 现状已部分有：`is_big_swing` + saturation clamp + `note: "之后请不要再在同方向 bump 好感"`（`npc_tools.py:796`）——**保留并加强为"里程碑门槛"**。

#### M-D · 收益递减（改代码，确定性）—— 解决 P-B

- `delta` 按当前值衰减：`value > 80` 时 `effective_delta = delta × 0.3`；`value > 95` 时 `× 0.1`。纯算术。
- 效果：**"保持在最高"没有增量收益** → LLM 与玩家都失去硬顶动机。

#### M-E · reset / 新群后关系如何延续（改代码 + 改契约）—— 解决 C6 后半句

现状：`rpg_reset` 用 `wipe_session` 清空**本局数值**，但 NPC 的默认姿态不随之改变。

方案：**区分"本局数值"与"跨局关系档案"**：
- **本局数值**（`npc_player_affinity.value`）→ reset 清空，符合直觉。
- **关系档案**（里程碑 + 关系摘要）→ **作为 NPC 的长期记忆保留**（写入 NPC 的 canonical/长期层），reset 不清。
- **reset 时给一次显式选择**（这是负责人仅有的控制权之一，符合开放问题 5「只有 reset/forget」）：
  - 「**延续关系**」→ 保留里程碑，NPC 记得你。
  - 「**重新认识**」→ 清空里程碑，关系回到起点。
- **关键设计**：**"重新认识"必须是有吸引力的默认**——因为里程碑可重新解锁（内容可复用），且**不再"默认最高"**（M-C 门槛生效）。这样"开新群"从"复制满好感"变成"重新体验一遍关系"。

#### M-F · 必修确定性 bug（改代码，P0）

- 修 `narrative_package.py:1502` 的工具名匹配：`update_npc_affinity` → `update_npc_affinities`。
- 修 `stage_changed` **无生产者 + `old_stage`/`new_stage` 缺失**：在 `_apply_affinity_for_npc` 里比较 `old_stage != new_stage`，把 `old_stage`/`new_stage`/`stage_changed` 写入返回 dict（**纯状态比较，合规**）。或直接由 M-B 的里程碑提示取代它。
- **同源命名修正（§3.2.2 的 4 处）**：`narrative_package.py:175`、`intent_supervisor.py:47`/`:123`、`tool_executor.py:164` 统一为 canonical 名（或双名兼容）。**修正后 ±25 钳制与 min_interval 节流才对 canonical 工具生效**——这直接给 C6「反复攻略」去掉一个机制放大器。

### 3.4 评估：是否应该直接删除好感度数值系统？

**我的判断：不删数值，但把数值"降级为内部温度计"，并删除它的"玩家可感承诺"。**

理由（4 条）：

1. **数值本身是确定性的、有用的状态载体**。它是驱动 prompt 注入与门槛判断的最简梯度。删掉它，需要重造一个等价的状态量——**没有收益**。
2. **数值不是根因**。根因是 G1–G6：**"数值是唯一差异源" + "中间态无行为差异" + "无里程碑" + "无内容产出"**。删掉数值只解决了"看得见一个数"，但玩家本来就看不见它——**删了等于没改**。
3. **数值对 LLM 有用，对玩家无用**。它不该被"玩家"消费（本就不可见），只该被"机制"消费（门槛、递减、阶段）。**它的正确角色是温度计，不是关系本身。**
4. **但必须删掉"数值的玩家可感承诺"**：即不要再用任何方式暗示"好感度可以刷"。一旦"关系深度"由**里程碑集合 + 阶段行为契约**承载，数值退居幕后，C6 的三个子问题（P-A/B/C）全部被机制解决。

> **一句话结论**：**保留 `value` 作为内部状态；把"玩家可感知的关系深度"改为「里程碑集合 + 阶段行为契约」驱动。** 数值从"关系"降级为"温度计"。
> ⚠️ 若负责人坚持"数值必须删"，我的最小可行替代是：**用"已解锁里程碑数"（0–N 的整数）直接替代 `value` 作为唯一关系状态**——但这需要重写 `compute_stage` 与所有 `+delta` 调用点，**收益与风险不成比例**，故不推荐。

#### 4.2.1 关键裁决：第一轮"AI 提议 2-3 个走向，玩家点头/微调/否决"是否仍然成立？

**我的判断：❌ 不再成立，应废弃。** 理由（4 条，全部有据）：

1. **E3 = 「A，但我想要新鲜感和意外感」**。菜单**杀死意外感**——你看见选项的那一刻，惊喜就没了。E3 明确要"意外"，而菜单是"意外的反面"。
2. **数据反证**：纯"继续"仅 **1.4%**，中位数 65 字散文。**如果玩家想要菜单，他会选菜单（"继续"就是最简菜单）**。但他不选——他写 65 字。**菜单会把"65 字散文创作"降级成"点选"，直接摧毁产品灵魂**（也摧毁 ①②里"每句台词更好"的产品 KPI）。
3. **E2 = 「知道，但嫌麻烦，也没什么用」**（针对编号选项类机制）+ 编号选项合规率仅 **44.9%**（契约要求"末尾 3-4 编号选项"，但 `contract_pipeline.py` 与 `skills/rpg-style-core/SKILL.md` 两个注入点互相抵消）。**菜单机制已经被实测证明是负资产。**
4. **开放 Q2 = 「我想消费一个写好的世界」**。消费者**接收**世界，不从菜单里**挑选**世界。菜单是"共同创作"姿态，与"消费"姿态冲突。

> **裁决**：把第一轮建议**替换**为——**"NPC 主动出手 + 情境锚点"**：玩家不需要"决定走向"，只需要"**回应**"。**从"发起"降为"应答"。**

## ⑤ 记忆保持：独立需求线（C3 = 7 分，最高并列；D5 明确点名）

### 5.1 证据

- C3 评分：好感度 6 / 伏笔 4 / **记忆召回 7** / 奖励选择 4 / 区域剧情结算 3 / **叙事风格切换 7**。**记忆召回与叙事风格切换并列最高（7）。**
- D5 原话：玩家在乎的是「情绪价值、陪伴体验、角色还原度、**记忆保持**」。
- 现状【实测】：`recall_memory` 全周期仅 **1 次**；`recall_npc_history` 仅 **5 次**；`enable_kb_memory` **默认 false**（`_conf_schema.json:256`）；记忆召回触发依赖 `_intent_references_past`（`narrative_package.py:897`）——一个**关键词匹配**（"记得/回忆/之前/上次/过去/那时/以前"）。

> **诊断**：记忆是**最高价值（7 分）+ 最低激活（1 次）** 的功能。它不是"没价值"，是"**没被激活**"（第一轮结论）。而且它的激活依赖一个**关键词 gate**——这正是约束 5 警惕的"用关键词判断非确定性内容"的边缘案例（此处判断的是"是否引用过去"，比"叙事质量"轻，但仍是脆弱的启发式）。

### 5.2 规格（记忆保持需求线）

## ⑧ 世界时钟语义裁决（P0 前置，路径路线图依赖项）

> 触发：team-lead 复核出"玩家当前 zone 时间 vs 全局时钟"一致率仅 **39%**（9/18），且 B4 亲述「时间段切换是否合理」落在"想我接下来说什么"的 4 分痛区。路径把本条列为 **P0 行的前置依赖**。以下为 Q1/Q2/Q3 裁决。

### 8.0 先纠正一个测量口径：这是**四层时钟**架构，不是两个

代码取证（本轮）显示系统里存在 **4 个时间字段**，它们**不是一个东西**：

| 层 | 字段 | 写入者 | 语义 |
|---|---|---|---|
| **L1 · Scene 时钟（权威）** | `scenes.time_slice` / `time_slice_index` / `day_count` | `advance_scene_time`/`set_scene_time`（`state_machine.py:3528/3553`） | **每个玩家/每组场景的权威时钟**（`Scene` 注释："a group of players in the same zone with shared time"） |
| **L2 · 世界高水位** | `game_sessions.max_time_slice` / `max_time_index` / `max_day_count` | `_sync_world_clock`（`state_machine.py:3602`） | **单调**高水位 = "任一 scene 到过的最晚时间" |
| **L3 · 遗留全局时钟** | `game_sessions.current_time_slice` / `time_slice_index` / `day_count` | `advance_time_slice`/`set_time_slice`（`state_machine.py:2570/2595`，**无 scene 时的兜底路径**） | 旧全局时钟；**scene 推进时不会被更新** |
| **L4 · Zone 渲染戳** | `zones.time_slice`（`models.py:157`） | `update_zone_volatile`/`save_zone_snapshot` | **该 zone 当前已物化的环境（env/npcs/items）对应的时间** |
| （缓存） | `zones.volatile_cache.time_snapshots[time_slice]` | `save_zone_snapshot`（`state_machine.py:1720`） | **按时间索引的 overlay 缓存**（同一地点在不同时间长什么样） |

> ⚠️ **口径纠正（重要）**：39% 是拿 `zones.time_slice` 对比 **`game_sessions.current_time_slice`（L3）** 得到的。但 **L3 不是玩家的权威时钟**——`advance_scene_time` 只写 `scenes`(L1) + `max_*`(L2)，**根本不写 L3**。所以 39% 里混入了"L1 与 L3 分叉"这一**额外的、与 zone 无关的**不一致。**正确参照系 = `get_current_time_slice_for_player`（`state_machine.py:3630`，scene 优先、global 兜底）。** 建议路径按此口径**重测基线**，再定 Gate 阈值。

### 8.1 Q1 · 语义裁决：选 **(a)**

**四个选项与裁决**：

| 选项 | 定义 | 裁决 |
|---|---|---|
| **(a) 当前时间** | 该 zone 此刻的时间切片，必须与**玩家权威时钟（L1）**同步 | ✅ **采纳** |
| (b) 上次到访时间 | 玩家上次来时的快照，允许落后 | ❌ 否决——会让 `time_snapshots`（同一地点昼夜不同的 overlay 缓存）失去意义 |
| (c) 其他 | — | — |
| **(d) 废弃/降级 L3** | `game_sessions.current_time_slice` | ⚠️ **强化为"必须清除全部 L3 读取点"**——它不是"死字段"，是**僵尸字段**（写入已停、读取未停），见 **§8.4**。只改写入端不改读取端，这 14 处会继续读一个**永久冻结**的值 |

> **权威语义定义**：`zones.time_slice` = "该 zone 当前已物化的环境（env/npcs/items）所对应的那个时间切片"——一个**派生字段（render stamp）**，不是独立事实。对玩家当前所在 zone，它必须等于玩家权威时钟（L1 scene）。

**关于"混用即缺陷"——我不同意，且这个区分对施工很重要**：写入路径的 (a) 语义与 `time_snapshots` 的按时间缓存是**两个不同对象**，不是同一个字段的两种语义：
- `zones.time_slice` = "现在物化的是哪个时间的场景" → **(a)**
- `time_snapshots[k]` = "这个 zone 在时间 k 长什么样" → 一个**按时间 key 的缓存**，既不是 (a) 也不是 (b)

**所以不存在真正的"混用"**；缓存侧是对的（"同一地点昼夜不同"正是想要的功能）。**缺陷只有一个：写入路径没有维护 (a)。** 具体两处，**均为确定性**：

1. **顺序 bug（结构性，每次非零耗时移动必现）**：`handlers/zone_tools.py:212-218` 取**移动前的** `current_scene.time_slice` → `:257` 用它物化目标 zone → 直到 `:455` 才 `advance_scene_time(steps=time_cost)`。→ 目标 zone 盖的是**移动前**的时间戳，而 scene 时钟已是移动后的。**`time_cost ≥ 1` 时必然错位**（实测两例"深夜公寓/午休"都属此类）。
2. **静止推进不同步**：`advance_scene_time`/`set_scene_time` 只改 `scenes`，**不重新物化玩家当前 zone**。

**结论**：**(a) 是对的一侧；错的是写入路径没有做到 (a)，而不是缓存侧。**

### 8.2 Q2 · 不变量（供路径写成 Gate）

- **INV-1（同步；对 team-lead 的 A 做参照系修正）**：
  `zones.time_slice == get_current_time_slice_for_player(session, player_entity_id)`
  ——**参照系必须是玩家权威时钟（L1 scene），不是 `game_sessions.current_time_slice`（L3）**。基线按旧口径 39%；**按新口径需重测** → 目标 **100%**。
- **INV-2（渲染一致性；替换 team-lead 的 B）**：渲染玩家当前 zone 时，**被应用的快照 overlay 的 key 必须 == 玩家权威时钟**（"绝不在早晨套用深夜快照"）。
  —— team-lead 原 B（"缓存快照不得携带与命中时刻不一致的时间切片"）**按构造天然成立**（key 就是时间），真正要 gate 的是**套用时刻 == 命中 key**。
- **INV-3（原子性；设计规则，非断言）**：`zones.time_slice` **只能由"同时物化了该 time_slice 场景内容"的路径写入**（stamp 与 materialization 原子）。**禁止裸写** `UPDATE zones SET time_slice=?`——`scene_generator.py:336-339` 的 no-LLM 分支就是一处裸写。
- ⚠️ **`max_time_index > time_slice_index`（12/18 会话）是 reset/forget 指纹，属正常**（高水位单调，代表"世界曾到过这里"）→ **不得纳入 INV-1**，也不应"修复"。

### 8.3 Q3 · 写路径 vs 读路径：**修写路径（主）+ 读路径 guard（辅）；读路径单独修被否决**

**为什么不能只修读路径**：`environment_desc` **内嵌了时间**——`models.py:207` 把 `[{time_slice}]` 与 `environment_desc` 一起渲染进上下文（`📍 公寓 [深夜]` + "昏暗的…"）。若只改读路径（时间取权威时钟、zone 不存时间），会出现**"现在是早晨" + "昏暗深夜的房间"**这种**更严重的自相矛盾**。→ **必须重新物化 env**，即写路径。

**写路径修法（两处，均为确定性，无叙事质量判定）**：
1. **顺序修正**：`move_to_zone` 中把 `advance_scene_time(time_cost)` **提到** `get_or_create_zone` **之前**，用**移动后**的 `time_slice` 物化目标 zone。**改一处顺序即消灭结构性 bug。**
2. **推进后重物化**：`advance_scene_time`/`set_scene_time` 改变玩家时钟后，**重新物化玩家当前 zone**——把 `scene_generator.py:277-341`（`ensure_zone_exists` 里已有的"快照命中→套 overlay / 未命中→LLM 刷新 / 无 LLM→仅盖戳"）**抽成共享 helper 并复用**；**优先走快照缓存（零 LLM），miss 才刷新**（控制成本）。

**读路径 guard（保留，不替代写路径）**：玩家可见的时间**永远取权威时钟**，不取 `zones.time_slice`（zone 供环境、时钟供时间）。`zone_tools.py:89` 已部分如此（`time_slice=scene.time_slice if scene else zone.time_slice`），保留并推广到 `get_context_text`。

**对 reset / forget 回滚的影响**：
- **reset**：`rpg_reset` → `wipe_session`（`commands.py:955`）连 `zones` 一起清 → **zone 层自动一致，无需额外回滚**。✓
- **forget（回溯一轮重选）**：**zone 层不要独立回滚**。`zones.time_slice` 是**派生字段**，派生字段应**从真源重算**，而非独立恢复。做法：
  1. forget 恢复时钟（**L1 scene**；L3 已停写，无需回滚）；
  2. **重跑 INV-1 的写路径同步**，从恢复后的时钟重新物化玩家当前 zone；
  3. **不清 `volatile_cache.time_snapshots`**——按时间 key 的 overlay 可复用，清了只会增加重生成成本；
  4. **L2 `max_*` 高水位不回滚**（单调），只回滚 **L1**。
  → 保持**单一真源（时钟）**，避免出现第二条会分叉的回滚路径。

### 8.4 L3 不是"死字段"，是"僵尸字段"（team-lead 复核 + 本轮扩充）

team-lead 复核：`_sync_world_clock` 只写 `max_*`，**不写 `current_time_slice`** → L3 写入已停。**但读取没停。** 本轮进一步普查发现，L3 的读取面**比 team-lead 给的 7 处更大**，因为存在一个 **`get_time_info()` 读取中枢**：


`get_time_info` 全库被调用 **14 处**（含 `prompt/assembler.py`、`narrative_package.py:1354`、`router_context.py:246`、`life_engine.py:383` 等 LLM 上下文装配点）。

**分类（必须区分，否则会误伤正确的 fallback）**：

| 类别 | 站点 | 判定 |
|---|---|---|
| **A · 正确（scene 优先的 fallback）** | `assembler.py:321/853`、`progression_tools.py:106`、`zone_tools.py:218/430/463`、`_base.py:641`、`state_machine.py:3637`（`..._for_player` 兜底） | ✅ 保留（`if scene: 用 scene else: 读 L3`） |

### 8.5 `location_changed` 门控：一个**独立的体验缺陷**（建议单列）

team-lead 补充：`zone_tools.py:453` 的门控含 **`location_changed`**：

```python
:451  # Advance SCENE time based on time_cost (not global)
:453  if active_scene and time_cost > 0 and location_changed:
:455      new_time = await ...advance_scene_time(session_id, active_scene.scene_id, steps=time_cost)
```

**我的判断：值得单列**，理由：
1. 它与 B4「**时间段切换是否合理**」**同源**（都是"时间没有按叙事预期推进"），但**成因不同**（R21 是顺序错位、本条是门控过严）→ 修法不同，必须分开。
2. 但它是**能力缺口**，不是**正确性 bug**（不产生数据不一致）→ 优先级 **P1**，且**优先用 prompt/契约修**：在契约里告诉 LLM"玩家等待/休息/过夜时，应调用 `set_time_slice` 或 `move_to_zone(time_cost>0)` 推进时间"——**保持"LLM 调工具"的设计意图（C7），不动代码**。代码侧仅在"契约无效"时才放宽门控。
